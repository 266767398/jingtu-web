## 一、状态口径

- **已接入**：后端路由已挂载，主站或独立页面存在可达入口。
- **API 已挂载**：服务端可调用，但主站没有已接入 UI。
- **文件存在/未接入**：前后端代码存在，主站未加载脚本或没有入口。
- **存在阻断缺陷**：代码和入口存在，但当前实现不能作为完整、可靠能力发布。
- 权限栏描述实际路由中间件；“公开”不表示数据一定可匿名读取，部分列表还会按登录状态或可见性过滤。

### 2.1 直播能力的实际边界

- 房间 CRUD、状态、观众、评论、点赞和主站面板存在。
- 创建房间只把 RTMP/HLS 字符串写入数据库；仓库没有 RTMP ingest、转码器或 HLS 输出服务，不能据此宣称可直接推流播放。
- 公开直播开播后通过现有通知服务通知成员；通知服务内部失败不会把开播请求变为 500。
- 列表、详情、进入、离开、观众、弹幕和点赞接口统一限制私密直播，仅主播本人和管理员可访问。
- `/user/history` 位于参数路由之前；重复进入/离开会按有效观众记录重算人数。
- 弹幕、点赞、观众数主要通过 HTTP，并无直播专用实时广播。

### 2.2 实时能力

- `/ws` 已启用并由主站连接，承载在线状态、位置、私聊、群聊、输入状态、历史请求和通知事件。
- 握手验证签名 Session Cookie，并从 Session Store 取得 `userId`；消息处理忽略客户端自报 `userId`。
- 生产 Origin 校验只有在请求带 Origin 且白名单非空时才拒绝，因此“无 Origin”或空白名单仍会放行。
- 在线用户、连接、群成员缓存都在单进程内存（`ws` 句柄不可序列化，跨实例广播需 Redis pub/sub 或粘性会话），未引入该方案前不适合多 worker。CSRF Token 已于 2026-09-12 改为本地 Map + Redis 双写，可跨 worker 校验；限流计数同理已共享化。

## 三、认证与权限

### 3.1 Session

- `express-session` 使用 MySQL Store，加载失败时回退 MemoryStore。SQLite 模式（`JINGTU_DB_ENGINE=sqlite`）下 Store 连不上 MySQL 同样回退 MemoryStore（登录态不跨进程持久化）。
- Cookie 有效期 7 天并 rolling 刷新，`httpOnly: true`、`sameSite: 'lax'`。
- 登录成功会 regenerate Session。每个 `/api` 请求会尝试查库确认用户仍存在且未封禁；查库失败时 **fail-closed（返回 503）**，不再放行（2026-08-27 加固，修正此前「放行」实现）。
- Cookie `secure` 现由 `trust proxy` + `req.secure` 自动判定（`secure: 'auto'`）：仅当请求经 HTTPS 到达时才带 `Secure`。`trust proxy` 已在 `server.js` 按 `TRUST_PROXY` 配置（生产默认 `1`）。代理部署需确保 `TRUST_PROXY` 正确，否则 `req.secure` 不可靠。

### 3.2 实际授权模型

- `requireAuth` 只检查 `req.session.userId`，失败返回 401。
- `requireAdminCompat` 要求 `admin` 或 `super_admin`。
- `requireRole(...roles)` 实际按最高角色等级做阈值比较，不是允许角色集合匹配。
- 当前业务授权主要是上述固定角色与资源所有权检查。权限组支持内置组、自定义组、继承、成员与 `can_*` 配置，但大部分业务路由不读取这些权限键，不能称为已全面启用的细粒度 RBAC。
- 收藏推荐接口此前误用 `requireRole(ROLE_LEVEL.ADMIN)`（`ROLE_LEVEL.ADMIN` 不存在，等效要求等级 0，形成任意已登录用户权限绕过）；**现已改为 `requireAdminCompat`，仅 `admin`/`super_admin` 可调用 ✅ 已修复**。
- `pending` 主要体现为用户审核字段，不是 `ROLE_LEVEL` 中独立角色；各接口是否限制未审核用户取决于具体查询/中间件。

### 3.3 密码与敏感字段

- 本地密码使用 bcrypt，rounds = 12。
- 强度校验要求至少 8 位，并同时含大写、小写和数字；**不要求符号**。
- 登录失败计数和 `locked_until` 提供账户锁定；认证入口另有 IP 限流。
- 密码重置为邮件验证码三步流程。邮件能否发送取决于 SMTP 配置。
- `sanitizeUser()` 对部分用户字段分级返回；`.env` 读取接口会掩码常见敏感项。不能由此推断所有路由响应和日志都已统一脱敏。

## 四、安全中间件与实际边界

### 4.1 启用顺序

`server.js` 的主要顺序为：

1. CORS、压缩、手工安全响应头；
2. `/api` 全局限流、可疑路径检测、WAF；
3. 进程内 metrics、API 版本和请求大小限制；
4. `express.json()`；
5. `/uploads`、`/assets`、`public` 静态目录；
6. Session、账户有效性检查、分层限流、CSRF；
7. 业务路由。

顺序直接决定以下边界：WAF 位于 JSON 解析之前，静态目录位于 Session 之前。

### 4.2 限流

| 限流器 | 实际挂载 | 阈值 |
|---|---|---:|
| `ddosLimiter` | 全部 `/api` | 600 次/IP/分钟 |
| `loginBruteForceLimiter` | `/api/auth/login`、`/api/auth/vrchat-login`、`/api/login` | 5 次/IP/15 分钟，成功请求跳过 |
| `uploadLimiter` | 仅 `/api/album/upload`、两个并不存在的旧 profile upload 路径、`/api/admin/group-image` | 10 次/IP/分钟 |
| `adminLimiter` | `/api/admin`，以及若干与真实 `/api/admin/...` 路由不一致的旧前缀；`/api/migration` 有效 | 30 次/IP/分钟 |
| `searchLimiter` | `/api/search` | 20 次/IP/30 秒 |

因此不能概括为“所有上传和全部后台接口都有专用限流”。所有 API 至少受全局 600 次/分钟限制。`middleware/rate_limit.js` 中还有其他限流器定义，但除个别认证路由引用外，不代表主入口已启用。

计数存储（2026-09-12）：全站 12 处 limiter 的 store 统一为 `middleware/rate_limit_store.js` 的 `HybridStore`——Redis 可用时以 `cache.incr()` 原子自增（键 `rl:<limiter名>:<IP>`）实现跨实例共享计数，未配置 `REDIS_HOST` 或 Redis 报错时回退内嵌 `MemoryStore`，行为与共享化之前一致。

### 4.3 WAF 与可疑请求检测

- WAF 已注册，按有限正则检测 SQL 注入、XSS、路径遍历、LFI/RFI 和 shell 特征，命中返回 403。
- WAF **注册于 `express.json()` 之后**（P1-3 加固，2026-09-04），除 URL/query 外还实际扫描已解析的 JSON `req.body`：字符串值、对象 key 均检测，并对内容做 URL 解码复扫（覆盖 `%3Csvg onload` 编码与 `%253C` 双重编码），带 `g` 标志正则每次重置 `lastIndex`。早期文档中「WAF 先于 JSON 解析、Body 扫描无效」的说法已失效。
- 正则 WAF 只是一层启发式过滤，可能漏报或误报，不能替代参数化查询、输出编码和资源权限校验。
- `suspiciousRequestDetector` 仅拦截**根路径段**命中的已知探测路径（WordPress、phpMyAdmin、shell、system 等）以及任意层级的 `.env`/`.git` 文件探测；改为“根路径段”匹配后，不再误伤应用自身嵌套路由（如 `/api/admin/analytics/system` 此前会被 404）。

### 4.4 CSRF

- `GET /api/csrf-token` 生成 32 字节随机 Token，绑定 Session ID，有效期 1 小时，可重复使用；存储为本地 Map + Redis 双写（`csrf:<token>`，TTL 1 小时），本地 Map 为权威副本、Redis 供跨 worker 校验；本地 Map 每 15 分钟清理，超过 10000 条时再淘汰一半最旧记录。
- 所有 `/api` 下非 GET/HEAD/OPTIONS 请求默认校验 `x-csrf-token`。
- 豁免包括本地/VRChat 登录、登出、初始化、密码重置及 Setup 保存/测试；Migration 写操作不豁免。
- `/api/login`、`/api/2fa`、`/api/logout` 要求管理员并执行 CSRF 校验。
- CSRF 失败路径没有调用 `securityAlert.onCsrfFailure()`，所以文档不能声称 CSRF 失败一定进入安全告警统计。

### 4.5 CSP、CORS 与传输

- 未使用 Helmet；`server.js` 手工设置 CSP、`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy`，生产环境追加 HSTS。
- CSP 已移除 `unsafe-eval`，但 `script-src` 和 `style-src` 仍允许 `unsafe-inline`；`index.html` 与 `migration.html` 仍含内联脚本，不能称为严格 CSP。
- 应用监听 HTTP，TLS 依赖反向代理。HSTS 只有应用识别为 production 时写入。
- `CORS_ORIGINS` 未配置时传入 `origin: true` 且允许凭据，相当于反射请求 Origin，不是生产白名单。
- WebSocket `connect-src` 允许 `ws:`/`wss:`；生产应配合 HTTPS、代理 Upgrade 和严格 Origin 白名单。

### 4.6 SQL 注入、错误与 XSS

- 大部分值参数使用 `mysql2` 占位符；表名、字段、排序和条件等受控标识符仍有动态 SQL，依赖白名单。不能声称“所有 SQL 均无拼接”。
- 全局错误处理在非开发环境隐藏未捕获错误细节，且自 2026-09-10 起按类型分类响应（上传/请求体超限 → 413、JSON 解析失败 → 400、CSRF 令牌失效 → 403、其余 → 500）。响应格式已由 P2-6（2026-09-04/05）统一为所有 JSON 响应携带 `success` 布尔：`utils.ok()` 成功包络 + `utils.fail()` 扁平错误发射器（约 160 处、29 个文件），`sendError`/`handleError` 嵌套形态保留兼容已适配读取方的旧路由，前端 `safeErrMsg()` 两种形状均可解析。
- 前端多处使用转义函数，但仍有 `innerHTML` 写入未统一编码，不能声称所有用户输入都已安全输出。WAF 已覆盖已解析 JSON body（见 §4.3），但正则启发式仍可能漏报，XSS 防线仍依赖各渲染点审查。
  - ✅ **2026-08-27 修复两处存储型 XSS**：`members.js` 的 VRC 信任等级 `title` 属性与 `innerHTML` 未转义 → 改为 `escAttr()`/`esc()`；`posts.js` 编辑动态预览将 `mediaUrl` 直接拼入 `innerHTML` → 改为 `escAttr(mediaUrl)`。
  - ✅ **2026-09-10 修复 members.js 两处弹窗 XSS**：备注弹窗与举报弹窗标题将他人用户名未转义拼入 `innerHTML` → 改为 `esc(userName)`（commit 31bd807）。其余渲染点仍按本原则持续审查。

### 4.7 文件上传与静态文件

路由中的 Multer `limits.fileSize` 是各上传端点的**实际上限**；非上传类请求仍受全局 `requestSizeLimiter` 卡口约束（默认 20MB 总闸、非上传 POST/PUT 5MB，上传类路径保留 550MB 安全闸）。上传类路径（含 `/upload`、`/photos`、`/videos`）**不再**被 20MB 总闸拦截（2026-08-16 修复）。**这三个阈值（上传安全闸 / 普通请求体 / 小请求）自 2026-08-16 起由超级管理员在后台「系统设置 → 🛡️ 全局请求限制」可调**，持久化于 `system_config`（`req_max_upload_mb` / `req_max_body_mb` / `req_max_other_mb`），保存即生效无需重启；下限分别夹紧为 50/1/1 MB 防止误配卡死。结果如下：

| 场景 | Multer 配置 | 说明 |
|---|---:|---|
| 用户头像 | 5MB | 非上传路径，受全局 20MB 卡口兜底 |
| 群组图片 | 10MB | 同上 |
| 直播缩略图 | 20MB | 同上 |
| 聊天附件 | 100MB | 上传路径，由 multer 100MB 生效；2026-09-16 起支持图片/视频/语音三类（`createFileFilter(['IMAGE','VIDEO','AUDIO'])`） |
| 动态媒体 | 200MB | 上传路径，由 multer 200MB 生效 |
| 个人相册照片/视频（`/api/profile/albums/:id/photos`） | 200MB | 上传路径，由 multer 200MB 生效 |
| 主相册照片/视频（`/api/album/upload`） | 500MB | 上传路径，由 multer 500MB 生效（修复后真正可达） |

> 注：主相册上传上限 **500MB**（`server/routes/album.js:431` multer `fileSize`，前端 `public/js/main.js` 预校验同步 500MB）在 2026-08-16 修复 `requestSizeLimiter` 后已**真正可达**；个人相册/动态 200MB、聊天 100MB 同理。头像/群组/直播等非上传媒体端点仍受全局 20MB 卡口兜底。

- 通用 Multer 过滤信任文件名扩展名与客户端声明的 MIME；现所有上传路由经 `utils.secureUpload` 包装器统一调用 `validateUploadFile()`（扩展名 + 部分魔数校验），已列为启用防护。伪装扩展名的恶意文件会被拒绝。
- 聊天上传（`chat.js` `chatUpload`）复用同一 `secureUpload` 双闸，2026-09-16 起白名单扩展到视频/音频：`SAFE_EXTENSIONS` 增 `mp4/mov/webm/mkv/avi/ogg/mp3/wav/m4a`（聊天图片仍限 `jpg/jpeg/png/gif/webp`）；魔数表 `FILE_SIGNATURES` 以 null 通配字节覆盖 ISO-BMFF（mp4/mov/m4a 的 `ftyp`）、EBML（webm/mkv）、RIFF（wav/avi）三类容器，mp3 刻意不设魔数闸（ID3 标签/裸帧同步字 `0xFF Ex/Fx` 开头会误杀合法音频）。
- 群组图片会经 Sharp 处理并写入固定目标名；所有上传经 `secureUpload` 做扩展名 + 魔数校验，但图片类仍建议二次重编码以彻底消除恶意载荷。
- `/uploads` 现已加鉴权中间件（位于 Session 之后）：登录用户可直接访问；匿名请求须携带有效且未过期的公开分享令牌 `?share=<code>`（由分享接口在返回媒体 URL 时写入），否则返回 401。URL 枚举已不可行。缓存策略（2026-09-10 起）：`maxAge: 0` + `etag: true` 协商校验，头像目录响应 `public, max-age=86400`，其余私人媒体 `private, max-age=3600`（允许浏览器私有缓存、禁止共享缓存留存）。
- `/backups` 从未以静态目录公开：备份文件仅通过 `/api/admin/backups/*` 的管理员接口下载，不存在“知道文件名即可绕过”的静态暴露。
- 文件管理路由做解析路径/前缀约束，但仍应把存储目录权限、代理下载规则和符号链接策略作为部署边界。

## 五、监控、通知与运维

### 5.1 健康与指标

- `/api/health` 只报告服务正常和系统 VRChat 登录状态。
- `/api/health/live` 是公开进程探活；`ready` 公开检查数据库；`detailed` 需管理员，返回数据库延迟、CPU、内存和负载。没有 Redis 或 VRChat 连通性检查。
- `metricsMiddleware` 已启用，数据只保存在进程内，没有 Prometheus/OpenTelemetry 或持久指标端点。
- `res.json()` 会再调用被包装的 `res.send()`，随后 `finish` 又会计数；当前实现未及时设置 `_tracked`，请求可能重复计数。
- `routes/analytics.js` 读取旧的扁平字段，而 metrics 返回 `requests.total` 等嵌套结构，请求分析数据当前不可依赖。

### 5.2 日志与安全告警

- `logger.js` 提供应用日志文件与轮转；日志 API 还读取 `sys_oper_log`。主站已有操作日志界面。
- 安全告警以四个进程内 Map 统计登录失败、可疑请求、限流和 CSRF 键，每小时清空；统计值是不同键数量，不是持久事件数或 `critical/warning/info` 分级总数。
- WAF/可疑路径/限流会调用相关统计；当前 CSRF 中间件未接入 `onCsrfFailure()`。
- 达阈值后可通过站内通知发给管理员；没有持久告警表、外部告警平台或保证送达的邮件/Webhook 链路。

### 5.3 邮件、缓存与任务

- `notification-service.js` 在配置 SMTP 且用户开启 email 时直接发信，失败只记录日志，无队列持久化或重试。
- 通知服务读取 `SMTP_PASS`，通用 `mailer.js` 读取 `SMTP_PASSWORD`，Setup 写入 `SMTP_PASS`，配置名并不统一。
- `mailer.initMailer()` 和 `tasks.js` 未在 `server.js` 启动流程调用；邮件队列、任务失败邮件、日报等只能视为代码存在而未启用。
- Redis 依赖及缓存实现存在，但启动流程未调用缓存初始化；配置 Redis 环境变量不会自动启用缓存。

### 5.4 运维接口风险

- Setup 的 API 以项目根 `.env` 是否存在作为安装锁；独立页面公开可见，安全边界在 API。
- Migration 的 `test-connection`、数据库/表浏览、配置扫描等接口已统一要求 `requireAdminCompat`（整 Router 挂载），且为 POST 状态变更接口受 CSRF 中间件约束，不存在公开探测问题。
- 备份依赖外部 MySQL 命令；数据库密码通过 `MYSQL_PWD` 环境变量传入（不再进入命令行参数，避免被 `ps` 看到），备份目录仅经管理员接口访问。
- 导出接口已加固：单表/批量均限制 `LIMIT 50000` 防止全表内存爆炸；导出前对 `password`/`secret`/`token` 等敏感字段做脱敏（`***REDACTED***`）；每次导出记录审计日志（管理员 ID + 导出表）。仍建议后续对超大表改为流式导出。
- Webhook 只对部分事件接线；URL 没有 SSRF 目标校验，列表响应也未明确移除 secret，不能视为安全的通用事件平台。
- `admin-db.js` 未加载；数据库、文件、安全、分析、Webhook 等 API 的存在不代表对应运维 UI 已发布。

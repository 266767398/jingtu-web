## 一、安全审查与修复（维度 1）

### 1.1 已修复（P0 / P1）

#### P0-1 `/uploads` 分享令牌未绑定具体资源 → 越权访问全部私有媒体
- **根因**：`server.js` 的 `/uploads` 中间件仅校验"数据库中是否存在任一有效分享码"，**不校验请求的文件是否属于该分享**。攻击者可凭任意有效分享码访问站内任意私有媒体（他人头像、相册、群组文件）。
- **修复（方案 C，无需改表）**：基于 `share_links.type + target_id` 反查该分享内容授权访问的媒体相对路径集合，严格校验 `req.path` 是否在集合内；不匹配直接 401。已登录用户（`req.session.userId`）直接放行，不影响主流程。
- **验证**：
  - 无令牌访问 `/uploads/...` → `401`
  - 伪造令牌（`?share=AAAAAAAAAAAAAAAA`）访问 `/uploads/...` → `401`

#### P1-1 CORS 生产环境默认接受任意来源并携带凭据
- **根因**：`CORS_ORIGINS` 未配置时默认 `true`，等价于 `Access-Control-Allow-Origin: *` 且 `credentials: true`，存在 CSRF / 跨站数据窃取风险。
- **修复**：`server.js` 中未配置 `CORS_ORIGINS` 时改为**拒绝跨域（仅同源可用）**并输出告警日志；生产环境如需跨域须在 `.env` 显式限定域名列表。

#### P1-2 `trust proxy` 生产环境默认信任第一跳
- **根因**：`NODE_ENV=production` 时 `trustProxy` 默认 `1`，攻击者可伪造 `X-Forwarded-*` 绕过基于 IP 的限速/封禁。
- **修复**：默认 `false`；仅在显式配置 `TRUST_PROXY=1`（或具体跳数）时启用。

#### P1-3 导出接口泄露 `password_hash` 等敏感字段
- **根因**：`export.js` 的 `REDACT_KEYS` 脱敏名单未覆盖 `password_hash`、部分令牌类字段。
- **修复**：补全脱敏名单（含 `password_hash`、`reset_token`、`verify_token`、各类 `*_secret`/`*_key`/`*_token`），导出前递归剔除。

#### P1-4 `groups` 社群关系路由匿名可访问
- **根因**：`server/routes/groups.js` 多个敏感社群关系接口（成员刷新、成员列表、变更日志、快照、邀请、统计、世界列表、ID 检查）未挂载鉴权中间件，匿名用户可探测社群成员结构。
- **修复**：引入 `requireAuth`，对 9 个敏感路由统一加鉴权（保持与现有 `requireAdminCompat` 风格一致）。

### 1.2 待确认（P2，建议下轮处理）

| 项 | 类型 | 建议 |
|----|------|------|
| 登录 / 关键 API 缺失速率限制 | 限制绕过 | 在 `auth.js` 登录、注册、密码重置接口加基于 IP + 账号的滑动窗口限速（如 `express-rate-limit`） |
| 文件上传缺类型 / 大小白名单 | 限制绕过 | `server/uploads` 相关路由补 `fileFilter` + `limits`，仅允许图片/视频白名单 MIME 与体积上限 |
| CORS 具体域名未配置 | 信息泄露 | 部署时在 `.env` 写 `CORS_ORIGINS=https://域名1,https://域名2` |
| 个别用户输入拼接 DOM 转义遗漏 | 存储型 XSS | 全量 `innerHTML`/`insertAdjacentHTML` 接入 `esc()` / `DOMPurify` 审计（见维度 3） |

## 三、健壮性（维度 3）

### 3.1 已修复

- `public/js/core.js` 增加**全局错误兜底**：
  - `window.addEventListener('error', ...)`：捕获同步错误，非静默失败，过滤无害资源错误（`<img>` onerror、脚本加载错误），其余 toast 提示并 `console.error`。
  - `window.addEventListener('unhandledrejection', ...)`：捕获未处理 Promise 拒绝，避免"红字控制台 + 功能静默失灵"。

### 3.2 待办

- **业务 `fetch` 显式 try/catch**：全局兜底能防崩溃，但各业务接口应显式处理网络中断 / 401 / 500（loading 态清理、友好提示、重试）。建议抽 `api()` 统一封装层（已在 `core.js` 有基础 `api()`，扩展错误分支即可）。
- **`JSON.parse` 保护**：本地存储 / 分享链接解析处加 try/catch，避免坏数据致白屏。

## 五、插件机制（维度 5，模块化设计方案）

> 目标：在安全沙箱范围内允许用户自行安装浏览器插件 / 脚本并推送内容，且绝不逃逸沙箱、不扩散 XSS、不绕过鉴权。

### 5.1 目录与文件结构（模块化）

```
public/
  plugins/
    loader.js            # 插件加载器（核心，唯一信任边界）
    host.js              # 沙箱宿主：postMessage 桥 + 插槽渲染 + 净化
    registry.js          # 已启用插件清单（由 /api/plugins 填充）
  components/
    plugin-slot.js       # 可嵌入内容插槽（data-slot="home-sidebar" 等）
server/
  routes/
    plugins.js           # 列出/启用/禁用/审核插件（superadmin）
  services/
    pluginService.js     # 插件元信息读写、权限校验
plugins/                  # 用户/官方插件仓库（每插件一目录）
  example-widget/
    manifest.json        # { name, version, permissions:[...], entry, apiWhitelist:[...] }
    index.js             # 插件入口（沙箱内运行）
```

### 5.2 安全边界（关键）

1. **隔离运行**：插件入口在 `<iframe sandbox="allow-scripts" csp="...">` 或 Web Worker 中执行，**禁止访问父页 DOM、其他插件的 `localStorage`、Cookie**。
2. **权限白名单**：`manifest.json` 声明 `permissions`（如 `api:posts.read`、`ui:slot.home-sidebar`）。插件只能通过宿主提供的受限 API 通信，且后端代理接口强制走统一鉴权中间件（与核心接口同套 `requireAuth`）。
3. **严格 CSP**：插件 iframe 的 CSP 为 `script-src 'self' 'nonce-xxx'`、**禁止 inline script、禁止 connect 到任意外域**。
4. **内容净化**：插件推送的 HTML 经 `DOMPurify`（服务端 + 客户端双重）净化后，仅可渲染到声明的 `slot` 插槽，禁止操作核心 DOM / 表单 / 导航。
5. **管理审核**：superadmin 审核、启用、禁用插件；普通用户"安装"需明确授权弹窗，列出插件申请的权限。

### 5.3 宿主 API（插件可调用，受白名单约束）

```js
// 插件侧（沙箱内）
PluginHost.api('posts.read', { page: 1 })        // → 走白名单代理，带用户 token
PluginHost.render('home-sidebar', sanitizedHtml) // → 渲染到插槽（先净化）
PluginHost.onTheme(cb)                            // → 订阅主题变量变更
PluginHost.storage.get/set(key, val)             // → 仅插件私有命名空间
```

## 六、自定义布局（维度 6，模块化设计方案）

> 目标：支持组件自由移动调整，以及按钮颜色 / 背景 / 主题色等视觉参数自由设置。与布局存储解耦。

### 6.1 模块划分

| 模块 | 职责 | 文件 |
|------|------|------|
| 组件注册表 | 声明可拖拽组件（id / 默认插槽 / 渲染器） | `public/components/registry.js` |
| 拖拽引擎 | 基于 Pointer Events 的网格拖拽、位置持久化 | `public/ui/layout-editor.js` |
| 主题变量引擎 | 注入 / 更新用户级 CSS 变量 | `public/ui/theme-engine.js` |
| 布局调度 | 读取布局 JSON → 渲染组件到对应插槽 | `public/ui/layout-runtime.js` |

### 6.2 视觉参数

- 主题色、按钮色、背景色、圆角、密度等映射为 CSS 变量：`--accent`、`--btn-color`、`--bg`、`--radius`、`--density`。
- 用户修改后，`theme-engine.js` 将变量写入 `<style id="user-theme">`，实时预览、即时生效。
- 与系统主题（浅 / 深）叠加：用户变量优先于系统令牌，不破坏可访问性对比度。

### 6.3 拖拽

- 网格化自由布局（CSS Grid + transform），组件可跨插槽拖拽、排序、隐藏。
- 拖拽状态独立存储（见维度 7），与内容渲染解耦。

## 七、布局数据存储（维度 7，模块化设计方案）

> 用户布局数据可存储至服务器或缓存于浏览器本地，方案由布局引擎与存储层解耦。

### 7.1 存储抽象层

```
public/storage/
  layout-store.js   # 抽象：get()/set()/sync()，对上层屏蔽来源
  remote-layout.js  # 服务端 API 封装（/api/user/layout）
  local-layout.js   # localStorage / IndexedDB 封装
```

### 7.2 策略

- **本地为主、服务端为备**：未登录时存 `localStorage`；登录后 `layout-store` 自动 `pull` 服务端版本，`set` 时 debounce `push` 服务端。
- **冲突解决**：每条记录带 `version`（单调递增）或 `updated_at`；冲突以"服务端最后写入胜"并提示用户；可扩展为按组件粒度 merge。
- **表结构（后端）**：

```sql
CREATE TABLE user_layouts (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id     BIGINT NOT NULL,
  kind        VARCHAR(32) NOT NULL,   -- 'layout' | 'theme'
  data        JSON NOT NULL,           -- 布局/主题 JSON
  version     BIGINT NOT NULL DEFAULT 1,
  updated_at  DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user_kind (user_id, kind)
);
```

- **API**（均挂 `requireAuth`）：
  - `GET  /api/user/layout` → 返回 `{ layout, theme, version }`
  - `PUT  /api/user/layout` → 带 `version` 乐观锁，冲突返回 `409`

### 7.3 模块化保证

- `layout-store` 不依赖具体 UI；拖拽引擎只写位置、主题引擎只写变量，二者均通过 `layout-store` 持久化。
- 插件（维度 5）亦可通过 `PluginHost.storage` 复用同一抽象层，避免重复实现。

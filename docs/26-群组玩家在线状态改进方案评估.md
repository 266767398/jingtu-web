# 群组玩家在线状态 — 改进方案评估

> 背景：VRChat 隐私墙导致非好友玩家的在线状态无法被公开 API 准确获取（VRCX 同样只能准确追踪好友）。
> 本文档回答三个问题，并评估"服务器共享加载列表"方案的可行性，给出实现建议与优化方向。

---

## 一、先回答用户的三个疑问

### Q1. 非好友玩家在群组列表里会不会"不显示"？
**不会。** 当前 `loadGroupMembers` 直接从 `group_roster` 表查 `is_member=1` 的成员，与 `is_online` 无关，无论在线与否都会渲染为卡片。非好友玩家**永远会显示**，只是被后端当前的逻辑标成了"离线"样式。

所以用户担心的"不显示"在当前实现里不会发生——但会"误显示离线"，这正是体验问题的根源。

### Q2. 后端现在能否区分"好友 / 非好友"？
**能，而且已经天然区分了。** 关键在 `server/vrc.js` 的 `vrchatResolveOnlineStatuses`：
- 第一遍用 `/auth/user/friends` 批量拿到好友状态，`friendMap.has(id)` 为 true 即好友，状态最准确（含 location）。
- 第二遍非好友回退 `/users/{id}`，受隐私限制通常 `offline`、location 不可见。

**目前漏掉的一步**：`friendMap.has(id)` 这个布尔值没有被记录到 `group_roster` 表，前端也就无法据此区分样式。只需在 `vrchatResolveOnlineStatuses` 的返回对象里加 `isFriend` 字段，并把字段落库即可（见下文落地步骤）。

### Q3. 名片点开"在线"、列表"离线"为什么不一致？
名片（`openVrcMemberCard`）走的是**当前登录用户自己的 cookie**（`vrcWithFallback`），能看到该用户视角下的真实状态；列表刷新走的是**系统账号 cookie**，系统账号没加对方好友时只能看到"离线"。这正是本次第二十七/二十八轮修复的核心矛盾——用户自己看得到好友在线，但系统账号视角看不到。

---

## 二、方案 A（推荐先做）：好友 / 非好友 双样式 + "状态未知"

### 思路
- 好友：正常绿色状态点 + 真实在线状态（active/join me/busy…），与现在一致。
- 非好友：灰色/虚线状态点，标注 **"状态未知"**，不再伪装成"确定离线"。
- 这样直观区分"我知道他在线/离线"和"我无法确认"，消除"列表离线 vs 名片在线"的困惑。

### 落地步骤（改动小、风险低）
1. **`server/vrc.js` `vrchatResolveOnlineStatuses`**：好友分支的 `result.set` 已带 `source:'friends'`，回退分支带 `source:'user'`。统一补一个 `isFriend` 字段：
   - 好友：`isFriend: true`
   - 非好友回退：`isFriend: false`
   - 未解析到（`onlineMap` 里没有）：默认 `isFriend: false`（查询失败不误判）。
2. **`server/db_init.js`**：`group_roster` 增加列 `is_friend TINYINT DEFAULT 0`，并加迁移语句（与现有一致用 try/catch 兼容 MySQL 5.7）。
3. **`server/schedule.js` 与 `routes/groups.js`**：UPDATE `group_roster` 时把 `is_friend` 一并写入。
4. **后端接口返回**：`GET /api/group/members` 已经 `SELECT *`，无需改，前端直接读 `isFriend`/`is_friend`。
5. **`public/js/group.js`**：
   - 渲染 `group-member-card` 时根据 `isFriend` 加 class `unknown-status`；
   - 状态点改用第三种样式（灰色虚线），文案 `状态未知 / ?`；
   - `applyRosterUpdate` 增量更新也要同步 `isFriend` 与样式。
6. **CSS**：在 `public/css/` 对应文件加 `.group-member-card.unknown-status` 与 `.gm-status-dot.unknown` 样式，并 bump `index.html` 的 `?v=`。

### 收益
- 立刻消除"假离线"误导；用户一眼看出哪些状态可信、哪些不可信。
- 不涉及隐私绕过，完全合规。
- 不增加 VRChat API 调用量（好友列表本来就要拉）。

---

## 三、方案 B（用户提议）：收集用户加载列表共享到服务器

> 思路：A 客户端加载时把自己能看到真实状态的好友列表上报服务器 → 存入共享表 → B 用户先读服务器聚合信息，再合并自己本地的。

### 可行性评估

| 维度 | 结论 |
|------|------|
| 技术可行性 | **可行**，本质是一个"好友在线状态聚合缓存表"，后端 cron 已具备批量查询能力 |
| 隐私合规性 | **可行但需谨慎**：上报的是"谁在线"的公开聚合信息，不泄露好友关系链本体；但建议只上报 `vrchat_id + is_online + 时间戳`，不存昵称/私信等 |
| 实时性 | **弱**：依赖有人在线并加载页面才更新；若群里所有人都没开网页，聚合表就 stale |
| 覆盖度 | **有盲区**：只有当某成员同时是"上报者的 VRChat 好友"且"上报者当前打开了网页"时才有效；非任何人好友的玩家永远进不了聚合表 |
| 成本 | 中等：新增上报接口 + 聚合表 + 读路径合并逻辑 |
| 与方案 A 的关系 | **互补，不互斥**：方案 A 解决"展示可信度"，方案 B 解决"非好友也能看到部分真实在线" |

### 落地要点（若要做）
1. 新增表 `group_presence_share(vrchat_id VARCHAR(100), is_online TINYINT, source_vrchat_id VARCHAR(100), updated_at DATETIME, PRIMARY KEY(vrchat_id))`。
2. 前端在 `loadGroupMembers` 成功后，若已登录且绑定了 VRChat，调用 `GET /auth/user/friends`（自己 cookie）拿到的在线好友，批量 `POST /api/group/presence/report`。
3. 后端 `vrchatResolveOnlineStatuses` 与 `GET /api/group/members` 合并来源：好友(自己cookie) > 他人上报(聚合表) > 系统回退(offline)。
4. **重要**：前端展示必须标注状态来源（`来自好友 / 来自群友上报 / 未知`），否则又回到"假确定"。

### 结论
- 方案 B **可行但只能作为方案 A 的增强**，单独做价值有限（覆盖有盲区、实时性弱）。
- 若人力有限，**优先方案 A**；方案 B 作为后续迭代。

## 四、其他改进方向 / 优化建议

1. **状态来源标签化（最重要）**：无论方案 A/B，每张卡片都应显示状态可信度来源（✅好友 / 👥群友上报 / ❓未知），比单纯变色更清晰。
2. **系统账号加好友提权**：把 VRChat 系统账号主动加为群内活跃成员的"好友"，可立刻扩大系统视角的可见在线范围（治本但需运营配合）。
3. **在线统计口径修正**：`getGroupStatsSnapshot` 当前把"非好友 offline"算入 offline，导致"在线数"被低估。建议统计时区分 `is_friend=1` 的在线 / 全部 / 未知，前端分别展示"确认在线 X / 状态未知 Y"。
4. **轮询成本控制**：当前 30s 全量/分批刷新，系统账号 cookie 过期会跳过整轮。建议给"状态未知"的玩家降频刷新（如每 5 分钟），好友保持 30s。
5. **前端本地缓存**：客户端已用 `groupMembersCache`，可把"我自己的好友在线集合"存在 localStorage，离线时也能区分可信/未知，无需等服务器。
6. **点击名片即校正**：`openVrcMemberCard` 用自己 cookie 看到真实状态后，可顺手回写 `is_friend`/`is_online` 到服务器（即方案 B 的"按需上报"轻量版，比定时全量上报更实时）。

---

## 五、建议落地顺序

1. **第一步（立竿见影）**：方案 A —— 加 `is_friend` 字段、双样式、标注"状态未知"。零新增 API、合规、低风险。
2. **第二步（增强覆盖）**：第 6 点"点击名片回写" + 第 3 点统计口径修正，让好友在线数更准确。
3. **第三步（可选）**：方案 B 共享表，进一步覆盖非好友的可见在线，但需配套来源标签。

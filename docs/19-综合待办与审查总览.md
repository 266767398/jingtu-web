## 11.8.2 VRChat 群组同步逻辑（groups.js）改进专项

> 重点：本地群聊（11.8.1）与 VRChat 群组同步器（本小节）是**两套独立系统**——前者是站内自建群聊，后者是把 VRChat 官方群组（硬编码 `GROUP_ID`）的成员/在线状态同步进本站 `group_roster` 表供群组页展示。本小节只评后者。

### 🔴 B1 — 手动刷新丢弃 `is_in_game`（核心 bug）
- **证据**：`groups.js:567-574` 的 refresh `UPDATE group_roster SET ...` 字段列表为 `display_name, avatar_url, is_online, vrchat_status, location, world_name, is_friend, is_vrc_plus, age_verified, age_verification_status, profile_pic_override_thumbnail, user_icon, last_seen, synced_at` —— **没有 `is_in_game`**。而同一函数内 `info = onlineMap.get(...)` 的 `info.isInGame` 字段（`vrc.js:477/553` `vrchatResolveOnlineStatuses` 已返回）明明可用，却从未写入。
- **连锁影响**：`/group/members` 的 `web`/`ingame` 筛选（`groups.js:663-665`：`is_in_game=0/1`）与 `/group/stats` 的 `inGameCount`/`webOnlineCount`（`groups.js:746/760`）完全依赖 `is_in_game`。该字段**只有 `schedule.js` 周期任务（约每 N 分钟）写入**（`schedule.js:404/409`）。于是：用户点「刷新在线状态」→ 在线/离线/状态都更新了，但「网页端/游戏内」分类与统计**直到下一次 scheduled 任务才刷新**，中间一直是旧值。
- **修复（低风险、单点）**：在 refresh 的 `UPDATE` 中补 `is_in_game=?`，取值 `info.isInGame`（好友路径已由 `vrchatResolveOnlineStatuses` 给出；非好友/共享路径按 `isOnline && location && location!=='web' && VRC_INSTANCE_PATTERN.test(location)` 推导）；同时在 `results.push`（行 576）补 `isInGame` 字段供前端即时渲染。另：共享状态分支（`sharedMap` 命中时）也应按同样规则补 `isInGame`。

### 🟠 B2 — refresh 冗余 probe 调用（每次多 1 次 VRChat API）
- **证据**：`groups.js:487-498` 在 `vrcWithFallback` 的 run 里**先** `await vrchatGetUser(toProcess[0].vrchat_id, cookie)`（仅取第一个成员探活），若 401 才返回 `{status:401}` 触发 fallback；随后**再** `vrchatResolveOnlineStatuses(...)` 内部又对每个非好友成员各发一次 `vrchatGetUser`。
- **问题**：每次手动刷新凭空多 1 次 API 请求（探活），在 VRChat ~50 req/min 限流下纯属浪费；且 `vrchatResolveOnlineStatuses` 自身已能感知 401，外置 probe 是重复劳动。
- **修复**：让 `vrchatResolveOnlineStatuses` 在遇到「根 cookie 401」时返回 `{status:401, data:null}`，`vrcWithFallback` 据此触发降级，删除外置 probe，省 1 次请求/刷新。

### 🟠 B3 — 全局冷却跨用户阻塞
- **证据**：`lastSyncAt`/`lastRefreshAt` 是 `module.exports` 闭包内的模块级变量（`groups.js:92-93`），整个进程（含所有登录用户）共享一份。
- **问题**：用户 A 触发同步 → 用户 B 5 分钟内点同步直接返 429「同步冷却中」；用户 A 刷新 → 用户 B 30 秒内刷新返 429「刷新太频繁」。对单人站点是合理的 VRChat 限流保护，但对**多人同时使用**的站点，冷却变成了「全局互斥锁」，一人操作冻结所有人。
- **修复/取舍**：保留全局冷却作 VRChat 限流兜底，但**冷却判定改为「上次操作距今 + 仍有其他人在跑」而非纯全局**；或改为按 `userId` 记冷却（同一用户 30s 内不可重复，不同用户允许并发，由 `syncInFlight`/令牌桶兜底总量）。属设计取舍，非 bug。

### 🟡 B4 — `MAX_REQUESTS = 100` 静默截断
- **证据**：`groups.js:473-477` 在线刷新只处理 `members.slice(0, 100)`，第 101+ 名成员**永不更新在线状态**（仅打 warning 日志）。
- **问题**：2000 人规模群组，95% 成员在线状态只靠 `schedule.js` 兜底；若 scheduled 任务异常，这部分成员长期显示离线。
- **修复**：分页轮询（每批 ≤100，按 `last_seen` 游标翻页直到处理完或触限流冷却）；或加大依赖「群友共享状态（方案 B）」的占比，降低对系统账号逐人解析的依赖。

### 🟡 B5 — VRC 缓存后台刷新无 in-flight 去重
- **证据**：`/group/members/:vrchatId/vrchat`（行 1199-1209）与 `/detail` 路径，stale-while-revalidate 用 `setImmediate` 触发 `fetchVrcData` 后台写库；同一 `vrchatId` 在并发请求下会触发多次后台拉取（无 in-flight Map 去重）。
- **影响**：好友/成员详情页被多人同时打开时，对 VRChat API 发起重复拉取（限流压力），并重复写 `group_member_vrc_cache`。
- **修复**：维护 `Map<vrchatId, Promise>` 的 in-flight 缓存；同 id 并发只跑一次 `fetchVrcData`，其余 await 同一 Promise。

### 🟡 B6 — 命名/工程一致性小项
| 项 | 说明 | 建议 |
|---|---|---|

## 11.8.7 群聊实时位置重构 + 创建群 memberIds 校验（2026-08-26 已落地）

> 原群位置共享存在四类体验缺陷：① 幽灵标记（对端刷新/关页未点停止，本端标记永不消失）；② 位置开关走普通群消息（`sendGroupMessage`），被持久化+计未读，刷屏且违背「位置不持久化」设计；③ 每个群各起一个 `watchPosition` + 一个 `setInterval` 双重定位，浏览器多 watch 受限且冗余上报；④ 创建群 `INSERT IGNORE` 静默丢弃不存在的 `memberIds`。

### 改动清单

| 项 | 原状 | 落地点 | 新行为 |
|---|---|---|---|
| 幽灵标记清扫 | 位置栏 `[data-uid]` 仅在对端主动 `stop` 时移除；对端异常退出则永久残留 | `chat.js` `groupLocLastSeen`(groupId→userId→ts) + `startGroupLocSweep`(每 10s 清 >30s 未更新项) | 对端掉线/刷新后，本端标记 30s 内自动消失；`beforeunload` 再尽力广播一次 `stop` 兜底 |
| 位置开关不污染群聊 | `start/stopGroupLocation` 调 `sendGroupMessage` 发「开始/停止共享位置」文本 → 持久化+未读角标 | `chat.js` 改调 `sendGroupLocationToggle`(WS `group:location:toggle`)；服务端 `ws_service.js` 新增该信令广播 | 开关走独立信令，不进消息表、不计未读；他人收到后由 `appendGroupSystemLine` 渲染居中弱提示系统行（`chat.location_sys_start/stop`），刷新即丢、不刷屏 |
| 全局单例定位 | 每群各起 `watchPosition`+`setInterval`，多群并发 watch 受限、坐标双重上报 | `chat.js` 引入 `glWatchId`(唯一 watch) + `glGroups`(Set) + `glLastSent`(≥4s 节流)；`ensureGlobalWatch`/`stopGlobalWatchIfIdle` | 全站只起一个 watch，位置变化时向 `glGroups` 内所有群广播；最后一个群停止即 `clearWatch`；删除冗余 `setInterval`，上报节流到 ≥4s |
| 创建群 memberIds 校验 | `INSERT IGNORE` 静默丢弃不存在的 userId | `server/routes/chat.js` `POST /groups` 先做 `SELECT id FROM users WHERE id IN (?)` 校验，仅加有效 id，无效 id 收集进响应 `invalidMemberIds` | 无效 id 不再静默丢失、可排查；响应新增 `invalidMemberIds`（前端可忽略） |

### 关键设计点
- **单例定位**：`glGroups` 为 `Set`，`startGroupLocation` 仅 `glGroups.add(groupId)` + `ensureGlobalWatch()`，不再维护 `groupLocationTimers`；`stopGroupLocation` 仅 `glGroups.delete` + `stopGlobalWatchIfIdle()`。彻底消除「多群 watch 受限」与「watch+interval 双重发」。
- **节流**：watch 回调内 `now - glLastSent < 4000` 则跳过，避免高频移动刷屏（原 `setInterval(5000)` 的节奏由节流近似替代）。
- **幽灵标记**：以 `groupLocLastSeen` 时间窗判定，与「实时位置信令 `group:location:update`」解耦——只要对端持续上报就保持，停报 30s 即清。覆盖服务端无法感知「客户端是否在共享」的盲区。
- **信令不持久化**：`group:location:toggle` 仅经 WS 广播，服务端 `broadcastToGroup` 不落库；客户端系统提示行是纯 DOM，刷新群聊即消失，零未读、零消息污染。

**回归风险**：仅影响群实时位置共享与群创建成员校验两条链路；普通群聊消息、私信、WebSocket 在线状态均不受影响。建议部署后：① 同时开 2 个群的位置共享→确认只有 1 个定位请求（DevTools→Network→WS 帧）；② 对端停止/刷新→本端标记 ≤30s 自动消失；③ 开始/停止共享→群消息列表不再出现「开始/停止共享位置」文本、未读角标不增；④ 创建群传入伪造 memberIds→响应 `invalidMemberIds` 含之、有效成员照常入群。

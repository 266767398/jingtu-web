## 二、严重 (Critical)

### C-1 `.env` 文件包含弱口令 `MYSQL_PASSWORD=root` 且存在于本机磁盘

- **位置**: [.env](file:///d:/phpstudy_pro/WWW/jingtu-web/.env#L5)
- **现象**:
  ```
  MYSQL_USER=root
  MYSQL_PASSWORD=root
  ```
- **风险**: 即便 `.env` 已被 `.gitignore` 排除（见 [.gitignore L2](file:///d:/phpstudy_pro/WWW/jingtu-web/.gitignore#L2)），但本机一旦被未授权访问、备份外泄或被勒索软件打包，数据库即裸奔；`root` + `root` 是最常见的爆破组合。
- **修复建议**:
  1. 生产与开发环境均使用 16 位以上随机密码。
  2. `docker-compose.yml` 已通过 `${JINGTU_DB_PASSWORD:?...}` 拒绝占位默认值，本地裸机部署需同样口径：在 `server.js` 启动时若检测到 `MYSQL_PASSWORD=root` 直接 `process.exit(1)`。
  3. 在 `.env.example` 注释中明确禁止使用 `root`/`123456` 等弱口令。

## 三、高危 (High)

### H-1 `migration.js` 存在管理员级 SSRF 与凭据中转风险

- **位置**: [server/routes/migration.js L227-254](file:///d:/phpstudy_pro/WWW/jingtu-web/server/routes/migration.js#L227-L254)
- **现象**: `POST /api/migrate` 接收 `sourceDb` / `targetDb` 任意 host/port/user/password，由服务端发起 TCP 连接：
  ```js
  sourceConn = await mysql.createConnection({
    host: sourceDb.host, port: parseInt(sourceDb.port),
    database: sourceDb.database, user: sourceDb.user, password: sourceDb.password,
    connectTimeout: 10000
  });
  ```
- **风险**:
  - 管理员可借此让服务端探测内网端口（SSRF）。
  - 管理员凭据以明文形式经本接口中转并在日志中出现（[L257](file:///d:/phpstudy_pro/WWW/jingtu-web/server/routes/migration.js#L257) 将 `host:port/database` 拼进 logs）。
  - 该路由仅 `requireAdminCompat`（admin 即可），低于 `requireSuperAdmin`。
- **修复建议**:
  1. 路由权限收紧为 `requireSuperAdmin`，与 `/api/database` 一致。
  2. 对 host 做白名单或私网段拒绝（除本机/已知迁移源）。
  3. 日志中不得回显 password；建议仅记录 `host:port/database`。
  4. 移除 `sourceDb.password` 透传，改为使用服务端预置的连接配置。

### H-2 `database.js` 部分管理路由仅 `requireAdminCompat`，可被普通管理员滥用

- **位置**: [server/routes/database.js L244, L343](file:///d:/phpstudy_pro/WWW/jingtu-web/server/routes/database.js#L244)
- **现象**:
  - `POST /admin/db/optimize/:table`、`/repair/:table`、`/kill/:pid` 仅 `requireAdminCompat`。
  - `KILL ${pid}` 虽做了数字校验（[L347](file:///d:/phpstudy_pro/WWW/jingtu-web/server/routes/database.js#L347)），但普通管理员可任意杀掉数据库连接，影响在线用户。
  - `OPTIMIZE TABLE` / `REPAIR TABLE` 是重 IO 操作，普通管理员触发会造成库级影响。
- **修复建议**: 这些破坏性操作应提升至 `requireSuperAdmin`，与 `/api/ops/*` 运维面板口径一致。

### H-3 `server.js` 启动兜底逻辑可能从 `.env` 注入弱口令到 `process.env`

- **位置**: [server/server.js L10-L31](file:///d:/phpstudy_pro/WWW/jingtu-web/server/server.js#L10-L31)
- **现象**: `backfillEnvFromFile()` 在 `dotenv` 之后再次从 `.env` 兜底，凡是 `process.env[key]` 为空就用文件值覆盖：
  ```js
  if (process.env[key] === undefined || process.env[key] === '') {
    process.env[key] = val;
  }
  ```
- **风险**: 在容器/PaaS 场景下若 `.env` 被错误带入镜像，密码即被静默注入；与 H-1 结合使弱口令更难被发现。
- **修复建议**:
  1. 生产环境 (`NODE_ENV === 'production'`) 跳过该兜底逻辑。
  2. 或显式列出允许兜底的键（`PORT`、`LOG_LEVEL` 等非敏感项），其余一律不读 `.env`。

## 四、中危 (Medium)

### M-1 `server.js` 顶部 `app.get('/api/avatar/default', ...)` 路由未鉴权且未限流

- **位置**: [server/server.js L287-L304](file:///d:/phpstudy_pro/WWW/jingtu-web/server/server.js#L287-L304)
- **现象**: 接收 `req.query.name`，生成 SVG 并直接 `res.send(svg)`。虽然 `safeText` 做了 `&` `<` `>` 转义，但：
  - 未走 `/api` 限流链（在 `app.use('/api', ddosLimiter)` 注册之前的同层）。
  - 注入 `?name=<script>alert(1)</script>` 会被转义，但 `?name=` 任意字符串仍可拼接到 SVG，可用于图片 XSS 探测。
- **修复建议**:
  1. 将该路由移到 `/api` 限流挂载之后。
  2. 对 `name` 加长度限制（≤16 字符）与中文/字母过滤。
  3. 设置 `Content-Disposition: inline; filename=default.svg` 防止被当作 HTML。

### M-2 `auth_local_service.js /preview` 端点可能被用于账户枚举

- **位置**: [server/auth_local_service.js L284-L303](file:///d:/phpstudy_pro/WWW/jingtu-web/server/routes/../auth_local_service.js#L284-L303)
- **现象**: `GET /api/auth/preview?loginId=` 返回该账号的头像 URL。注释虽写"账号不存在与无头像不可区分"，但攻击者可通过 `displayName` 探测头像是否变化来枚举有效账户；该路由仅受 `authPreviewLimiter` 限流。
- **修复建议**: 对未登录请求统一返回 `null/null`，或要求登录后才可调用。

### M-3 `req.session.bannedCheckedAt` 缓存 30s 可被绕过

- **位置**: [server/server.js L391-L415](file:///d:/phpstudy_pro/WWW/jingtu-web/server/server.js#L391-L415)
- **现象**: 封禁状态每 30 秒查一次库，被封禁用户在窗口期内仍可访问。注释承认"最多延迟 30s 生效"，但若管理员紧急封禁攻击者，30 秒窗口仍可造成数据外泄。
- **修复建议**:
  1. 对敏感操作（修改密码、删除内容、上传）跳过缓存直接查库。
  2. 引入 Redis pub/sub 失效信号，封禁时主动通知所有进程清缓存。

### M-4 `panel_proxy.js` 通过本地子进程承载运维面板，攻击面集中在共享密码

- **位置**: [server/panel_proxy.js](file:///d:/phpstudy_pro/WWW/jingtu-web/server/panel_proxy.js) + [server.js L190](file:///d:/phpstudy_pro/WWW/jingtu-web/server/server.js#L190)
- **现象**: `/ops/*` 入口已升至 `requireSuperAdmin`，但面板自身用 Bearer Token + 共享密码鉴权，可"重置超管密码/清空用户数据/停杀服务"。一旦共享密码外泄，超级管理员账号被锁后也无法阻止横向操作。
- **修复建议**:
  1. 面板密码改为 PBKDF2 + 单盐，并写入 `panel/panel-auth.json`（已 gitignore）。
  2. 面板关键操作（重置超管密码、清空用户）要求二次 Web 端 `requireSuperAdmin` 校验，而非仅凭面板密码。
  3. 面板空闲关闭时间从 20 分钟下调到 10 分钟。

### M-5 `.htaccess` 部署在 Node.js 项目中基本失效

- **位置**: [.htaccess](file:///d:/phpstudy_pro/WWW/jingtu-web/.htaccess)
- **现象**: 项目由 Node.js (Express) 提供服务，Apache `.htaccess` 仅在 phpstudy + Apache 反代场景下生效；若直连 3456 端口或 Nginx 反代，这些规则全部失效。`RedirectMatch 403 ^/server/` 等关键防护在此情况下不生效。
- **修复建议**:
  1. 在 `server.js` 静态文件挂载处显式拒绝 `/server/`、`/node_modules/`、`/.env` 等敏感路径。
  2. 或在 `deploy/nginx/jingtu.conf` 中镜像 `.htaccess` 规则。

### M-6 `unhandledRejection` 仅记录不退出，进程状态可能已损坏

- **位置**: [server/server.js L795-L798](file:///d:/phpstudy_pro/WWW/jingtu-web/server/server.js#L795-L798)
- **现象**: 相对 `uncaughtException` 退出策略，`unhandledRejection` 只记日志不退出。Node ≥15 默认 `unhandledRejection` 会终止进程，此处覆盖了默认行为。
- **风险**: 某些未捕获的 Promise 拒绝可能使请求状态错乱（连接未释放、事务未回滚）。
- **修复建议**:
  1. 对 `unhandledRejection` 区分类型：数据库连接错误 → 退出由 PM2 重启；其余 → 记录并继续。
  2. 在生产环境加 `process.exit(1)` 兜底，借助容器/PM2 自愈。

### L-5 `CORS_ORIGINS` 默认空时仍 `cb(null, true)` 放行同源/无 Origin 请求

- **位置**: [server/server.js L163-L170](file:///d:/phpstudy_pro/WWW/jingtu-web/server/server.js#L163-L170)
- **现象**: `if (!origin) return cb(null, true);` 让无 Origin 的请求（服务器到服务器、curl）绕过 CORS 检查。这本身是同源/非浏览器场景的标准行为，但配合 SSRF 可放大影响。
- **修复建议**: 在生产环境将 `CORS_ORIGINS` 显式设为站点域名，并对 API 路由要求 `Origin` 与 `Referer` 一致。

## 六、缺失功能 / 改进建议

### S-1 缺少 CSP nonce 改造，仍保留 `'unsafe-inline'`

- **位置**: [server/server.js L204-L213](file:///d:/phpstudy_pro/WWW/jingtu-web/server/server.js#L204-L213)
- **现状**: CSP `script-src` 与 `style-src` 仍含 `'unsafe-inline'`，注释自承"待后续 nonce 改造"。
- **建议**: 使用 express middleware 为每请求生成 nonce 并替换模板中的 inline 脚本。

### S-2 缺少自动化依赖扫描

- **现状**: `package.json` 未配置 `npm audit` / `snyk` / `renovate`，CI 也未见 `audit` 步骤。
- **建议**: 在 `package.json` scripts 中加入 `"audit": "npm audit --audit-level=high"`，并在 CI 增加 `npm ci && npm audit`。

### S-3 缺少健康检查端点的依赖深度检查

- **现状**: `GET /api/health/ready` 未在本次审查代码中找到，仅 `server.js` 顶部对 `MYSQL_HOST`/`SESSION_SECRET` 做启动校验。
- **建议**: 增加 `/api/health/ready` 检查 DB ping、Redis ping、磁盘空间，供 K8s readinessProbe 使用。

### S-4 缺少请求体大小限制中间件的统一配置

- **现状**: `express.json({ limit: '20mb' })` 全局 20MB，但 `requestSizeLimiter` 的具体策略未在审查中确认。
- **建议**: 对 `/api/album/upload`、`/api/profile/photos/upload` 等上传路由单独限制；普通 API 路由限制为 1MB。

### S-5 缺少日志脱敏中间件

- **现状**: `console.error('[session] 封禁状态校验失败:', e.message)`（[L409](file:///d:/phpstudy_pro/WWW/jingtu-web/server/server.js#L409)）等可能打印出含 PII 的错误。
- **建议**: 引入 `logger` 的 redact 配置，对 `password`、`password_hash`、`sessionID`、`email` 等字段打码。

### S-6 缺少二次验证 (2FA) 与登录历史

- **现状**: 超管账号仅密码 + bcrypt；登录成功后未记录设备指纹/IP 历史。
- **建议**:
  1. 对 super_admin 强制启用 TOTP（`otplib`）。
  2. `sys_oper_log` 之外增加 `login_history` 表，记录 IP/UA/timestamp，异常登录邮件告警。

## 七、已具备的安全实践（肯定项）

为避免误读，下列已落实的实践应保留：

1. **SQL 参数化**: `mysql2` 全量使用 `?` 占位符；表名/字段名走 `mysql.escapeId` 或白名单。
2. **CSRF Token 绑定 sessionID**: [middleware/csrf.js L149](file:///d:/phpstudy_pro/WWW/jingtu-web/server/middleware/csrf.js#L149) 严格匹配，fail-closed。
3. **文件上传纵深防御**: 扩展名黑名单 + MIME 匹配 + 魔数校验 + 大小限制 + 限流。
4. **限流分层**: DDoS / 登录爆破 / 上传 / 管理后台 / 搜索 各自独立桶。
5. **CORS deny-all 默认**: 未配置时拒绝所有跨域，杜绝开发态 allow-all。
6. **生产环境强校验**: 缺 `SESSION_SECRET` / `ENCRYPT_KEY` / `GROUP_ID` 直接 `process.exit(1)`。
7. **密码哈希**: bcrypt rounds=12；密码强度校验要求大小写+数字+≥8 位。
8. **错误脱敏**: 非 dev 环境统一返回通用错误码与文案。
9. **优雅关闭**: SIGTERM/SIGINT 触发连接池/WS/Redis 顺序释放。
10. **封禁 fail-closed**: 校验失败返回 503 而非放行。
11. **会话固定攻击防护**: 注册/登录后 `req.session.regenerate`。
12. **路径穿越防护**: 相册路径用 `path.resolve` + `isWithinAlbum` 硬校验。

### 10.7 严格复审结论

1. **生产直接依赖三连高危**（mysql2/nodemailer/sharp）是全项目最紧迫行动项，`npm audit fix` 后必须跑冒烟回归（数据库连接、邮件发送、图片上传）。
2. **AUTH-1 锁定计数器竞态**是唯一被实锤的**逻辑漏洞**（非配置/依赖问题），修复成本一行业务代码，收益是账户暴力防护真正生效。
3. **WS-2/WS-1** 使 WebSocket 面成为第二高风险区：先加 `maxPayload` + `maxConnections` + 身份字段服务端权威化。
4. **IDOR-1/IDOR-2** 是最典型的"业务面越权"，一次性把内联 `req.session.role` 全量替换为 `requireRole` 即可收敛。
5. 前端主链路（帖子/评论/私聊渲染）均走 `esc()` 净化，**未发现可利用的存储型 XSS**——这是本轮唯一全绿的主线安全面。

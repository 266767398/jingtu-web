## 2. 通用约定（所有模块统一遵守）

### 2.1 响应包络

- 成功：项目既有约定为 `{ "success": true, ... }`（好友/关注路由即采用此包络，与早期 `{data:...}` 草案不同）；列表类返回 `{ "list", "page", "pageSize", "total" }`（分页）或 `{ "list", "total" }`（不分页）。
- 失败：`{ "error": "<可读中文文案>", "code": "<ERROR_CODE>" }`（复用 `server/utils.js` 的 `ErrorCodes` + `sendError`）。
- 前端 `core.js` 的 `safeErrMsg(d)` 优先按 `d.code` 取语言包（见 docs/09 第十五轮 B1 方案），故**新增错误码须同步进 6 语言包 `error.*` 命名空间**。

### 2.2 鉴权中间件（`server/auth.js`）

- `requireAuth`：登录即可（`req.session.userId` 存在）。
- `requireRole(...roles)`：角色校验（角色体系 `super_admin`/`admin`/`member`，无 guest）。
- `requireAdminCompat`：管理员兼容（超管或 admin）。
- `requireSuperAdmin`：仅超级管理员。
- 会话用户标识统一用 `req.session.userId`。

### 2.3 越权拦截通用规则

- 未登录 → `UNAUTHORIZED`(401)。
- 资源不存在 → `NOT_FOUND`(404)。
- 已登录但非资源所有者且无管理员权限 → `FORBIDDEN`(403)。
- 参数非法/缺失 → `BAD_REQUEST`(400) / `VALIDATION_ERROR`(422)。
- 写操作一律服务端二次校验归属，**前端隐藏按钮不等于后端放行**。

### 2.4 实时推送

- 落库后调用 `notificationService.notifyUser(userId, type, title, message, target)`；在线用户经 `ws_service`（`/ws`）实时下发。
- 聊天消息：私聊推接收方；群聊推所有在线群成员（按群订阅）。

### 2.5 分页约定

- 入参：`?page=1&pageSize=20`（默认 page=1、pageSize=20，上限 100）。
- 出参：`{ list, page, pageSize, total }`。

### 2.6 本次新增错误码（`ErrorCodes` 扩展）

| 错误码                     | HTTP | 含义             |
| ----------------------- | ---- | -------------- |
| `ALREADY_FRIENDS`       | 409  | 已是好友           |

| `SELF_FRIEND`           | 400  | 不能添加自己为好友      |

## 3. 模块 1 · 好友系统（新建）

### 3.1 数据结构

```sql
CREATE TABLE IF NOT EXISTS user_friends (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NOT NULL COMMENT '关系主体',
  friend_id INT NOT NULL COMMENT '关系客体',
  status ENUM('pending','accepted','blocked') NOT NULL DEFAULT 'pending',
  requested_by INT NOT NULL COMMENT '发起方 user_id',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_pair (user_id, friend_id),
  INDEX idx_friend (friend_id),
  INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

> 设计：单向行 + `status` 表示 `user_id` 对 `friend_id` 的视角。`accepted` 表示双向好友（插入两条对称 `accepted` 行便于双向查询）；`blocked` 由任一方设置即对该方向生效。

### 3.2 状态机

```
 none ──A 申请──▶ pending(u=A,f=B,requested_by=A)
 pending ──B 接受──▶ accepted（写 (A,B,accepted) + (B,A,accepted)）
 pending ──B 拒绝──▶ none（删除该行）
 accepted ──任一方删除──▶ none（删两条）
 * ──A 拉黑 B──▶ blocked(A→B)；B 视角不变
 blocked ──A 解除拉黑──▶ none / accepted
```

- 拉黑优先级最高：若 `A→B` 为 `blocked`，则 A 不能给 B 发私聊（模块 2 拦截 `BLOCKED`），B 也不能给 A 发（按对称规则或查询时双向判断）。

### 3.3 接口契约

| 方法     | 路径                                 | 入参                                         | 出参                                                                                 | 越权/错误                                                                          |
| ------ | ---------------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| POST   | `/api/friends/request`             | `{ targetUserId }`                         | `{ friendship:{...} }`                                                             | `SELF_FRIEND`；`ALREADY_FRIENDS`；`FRIEND_REQUEST_EXISTS`；target 不存在 `NOT_FOUND` |
| POST   | `/api/friends/respond`             | `{ requestId, action:'accept'\|'reject' }` | `{ status }`                                                                       | 只能响应发给自己的申请，否则 `FORBIDDEN`；`FRIEND_NOT_FOUND`                                  |
| DELETE | `/api/friends/:friendUserId`       | —                                          | `{ ok:true }`                                                                      | 非好友 `FRIEND_NOT_FOUND`                                                         |
| POST   | `/api/friends/block`               | `{ targetUserId }`                         | `{ ok:true }`                                                                      | `SELF_FRIEND`；`ALREADY_BLOCKED`                                                |
| DELETE | `/api/friends/block/:targetUserId` | —                                          | `{ ok:true }`                                                                      | `FRIEND_NOT_FOUND`                                                             |
| GET    | `/api/friends?status=accepted`     | query `status`                             | `{ list, total }`                                                                  | 仅返回当前用户视角                                                                      |
| GET    | `/api/friends/requests`            | —                                          | `{ incoming:[], outgoing:[] }`                                                     | —                                                                              |
| GET    | `/api/friends/status/:userId`      | —                                          | `{ status:'none'\|'pending'\|'accepted'\|'blocked', direction:'in'\|'out'\|null }` | —                                                                              |

### 3.4 权限与通知

- 申请/拉黑/删除均限定当前用户为 `user_id`（发起方）。
- 接受/拒绝仅限 `friend_id = 当前用户` 的 pending 申请。
- 申请后 `notifyUser(targetUserId,'friend_request',...)`；接受后互推 `friend_accepted`。

### 3.5 实现状态（第十六轮已交付）

- **后端**：`server/routes/friends.js` 已落地 §3.3 全部 8 个接口，契约与本文一致；工厂签名 `(notificationService)`，挂载于 `server.js` 的 `/api/friends`。
- **实际响应包络**：统一为 `{ success:true, ... }`（见 §2.1）；列表 `GET /` 返回 `{ list, total }`。
- **与 §3.3 的差异（实现增强）**：`GET /status/:userId` 实际返回 `{ status, direction, blockedByThem }`——比规划多 `blockedByThem` 字段（前端据此禁用私聊/互动按钮，实现「被拉黑」前端即时反馈）；`POST /request` 在「对方已先向我发 pending」时自动双向接受并返回 `status:'accepted'`。
- **状态机落地**：
  - 拉黑 `POST /block` 用 `INSERT ... ON DUPLICATE KEY UPDATE` 写单向 `blocked`，并 `DELETE` 对称行 —— 杜绝「拉黑却仍显示好友」。
  - 接受 `acceptFriendship()` 走事务：UPDATE 原 pending→accepted + `INSERT IGNORE` 对称 accepted 行。
  - 删除 `DELETE /:friendUserId` 双向清除（accepted/pending/blocked 任一视角非好友即 404）。
- **前端**：`public/js/friends.js`（IIFE：搜索加友 / 收发申请 / 好友列表 / 黑名单 / 私信跳转 `openChat`）+ `index.html` 桌面「🤝 好友」tab 与移动端底栏项 + `ui.js` 的 `switchTab` 分发 `showFriends()` + `public/css/10-social.css` 布局；6 语言 `friends.*`（27 键）已注入，`error.*` 17 码齐备。
- **单测**：`server/__tests__/friends.test.js`（22 例，jest + supertest + mock DB 层）覆盖申请/响应/删除/拉黑/状态/列表全路径，全过。
- **升级脚本缺口**：`user_friends` 仅由 `db_init.js` 覆盖全新安装；既有库需另补 `ALTER TABLE` / `CREATE TABLE` 升级脚本（见 §11 待办）。

## 6. 模块 4 · 关注（新建）

### 6.1 数据结构

```sql
CREATE TABLE IF NOT EXISTS user_follows (
  id INT AUTO_INCREMENT PRIMARY KEY,
  follower_id INT NOT NULL COMMENT '关注者',
  following_id INT NOT NULL COMMENT '被关注者',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_follow (follower_id, following_id),
  INDEX idx_following (following_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

> 单向关注；`UNIQUE(follower,following)` 防重复。`follower_id=following_id` 应用层拒绝。

### 6.2 状态（无状态机，单向）

| ------ | ------------------------------------ | ------------------ | ------------------------------------- | ------------------------------------------------------------ |
| POST   | `/api/follows`                       | `{ targetUserId }` | `{ ok:true, following:true }`         | `SELF_FOLLOW`；`ALREADY_FOLLOWING`(幂等返回成功)；target `NOT_FOUND` |
| DELETE | `/api/follows/:targetUserId`         | —                  | `{ ok:true, following:false }`        | `NOT_FOLLOWING`                                              |
| GET    | `/api/follows/following?userId&page` | query              | `{ list, page, pageSize, total }`     | —                                                            |
| GET    | `/api/follows/followers?userId&page` | query              | `{ list, page, pageSize, total }`     | —                                                            |

## 7. 模块 5 · 点赞（完善，已存在 `user_like` + `post_like`）

### 7.1 现状与歧义

- `post_like(post_id, user_id)` `UNIQUE(post,user)` → 动态点赞可多次插入/删除（toggle 幂等），统计 `COUNT`。✅ 符合「幂等 + 统计」。
- `user_like(from, to, like_date)` `UNIQUE(from,to,date)` → **每日一次**给用户点赞（可重复每天点），与「全局幂等 toggle」语义冲突。⚠️ 待决策（§12）。

### 7.2 统一抽象建议（目标）

引入通用点赞表，覆盖动态/用户/相册照片/评论等：

```sql
CREATE TABLE IF NOT EXISTS likes (
  id INT AUTO_INCREMENT PRIMARY KEY,
  target_type ENUM('post','user','photo','comment') NOT NULL,
  target_id INT NOT NULL,
  user_id INT NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_target_user (target_type, target_id, user_id),
  INDEX idx_target (target_type, target_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- 接口：`POST /api/likes/toggle {targetType,targetId}` → `{ liked:bool, count:int }`（幂等切换）；`GET /api/likes/status {targetType,targetId}` → `{ liked, count }`。
- 统计：`SELECT COUNT(*) WHERE target_type=? AND target_id=?`。
- 查询是否点赞：`EXISTS(...)`。

### 7.3 错误码

`INVALID_TARGET_TYPE`、`TARGET_NOT_FOUND`。

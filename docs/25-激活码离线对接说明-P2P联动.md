# 激活码离线对接说明（境途同游 × P2P 联动）

> 版本：2026-09-10（v4：新增 有效期机制 / CLI 过期识别与 `--expires` / 前端批量复制·导出 CSV / 即将过期标签）｜ 状态：已实现并测试通过（jest 26 套件 418/418 + CLI 冒烟）｜ 供 P2P 团队对接使用
> 核心保证：**激活码的生成、校验、消耗、作废、对账全流程均可完全离线完成**——不需要网站运行、不需要数据库、不需要联网。

---

## 1. 总览与集成场景

激活码系统由一个 JSON 数据文件 + 一组 Node.js CLI 工具 + 网站 Web API 三部分组成，三者读写同一份文件并共用同一把文件锁。

| 场景 | P2P 侧具备条件 | 推荐对接方式 |
|---|---|---|
| A. 完全离线 | P2P 机器有 Node.js（或可打包 CLI） | 直接调用本文 §5/§6 的 CLI 工具（验码 + 消耗） |
| B. 完全离线、任意语言 | P2P 是 C++/C#/Go 等 | 按 §3 的 JSON 结构自行只读校验；**消耗时调用 consume CLI**（遵守 §8 锁协议） |
| C. 有网络 | P2P 服务端可访问网站 | 调用 §7 的 Web 注册 API，由网站后端校验+消耗 |

**分发模型**：超管用离线工具生成激活码 → 得到 `activation-codes.json` → 将该文件（或其副本）随 P2P 软件分发/部署到 P2P 机器 → P2P 侧注册用户时本地校验并消耗 → 文件写回持久化。

**安全模型（务必知悉）**：激活码是纯随机字符串，本身不含签名/校验位。防伪依赖两点：① 32 字符字符集 12 位随机（32¹² ≈ 1.2×10¹⁸ 种可能，暴力猜测不可行）；② **数据文件只发给可信方**，不要把完整 JSON 公开——任何拿到文件里未用码的人都能注册。

## 2. 激活码格式规范

- 格式：`JT-XXXX-XXXX-XXXX`（`JT-` 前缀 + 3 段各 4 位，共 12 位随机字符）
- 字符集（32 字符，**已剔除易混淆的 0/O/1/I/L**）：
  ```
  23456789ABCDEFGHJKMNPQRSTUVWXYZ
  ```
- 正则：
  ```
  ^JT-[2-9A-HJ-NP-Z]{4}-[2-9A-HJ-NP-Z]{4}-[2-9A-HJ-NP-Z]{4}$
  ```
- 归一化规则（校验前必须执行，与网站后端一致）：
  ```
  normalized = String(input).trim().toUpperCase().replace(/\s+/g, '')
  ```
  即：去首尾空白 → 转大写 → 去所有内部空白。**用户输入 `jt-ab2d-e3fg-h5jk`、`JT-AB2D E3FG-H5JK` 均视为同一码。**

## 3. 数据文件格式

文件路径：`server/data/activation-codes.json`（网站侧默认位置）。

**自定义路径**：所有 CLI 与服务层均支持 `--file <路径>` 参数；网站进程可用环境变量 `ACTIVATION_CODES_FILE` 指定任意路径。离线部署时激活码文件可放任意位置，分发时告知 P2P 侧路径即可。

```json
{
  "version": 1,
  "codes": [
    {
      "code": "JT-AB2D-E3FG-H5JK",
      "created_at": "2026-09-08T08:30:00.000Z",
      "created_by": "offline-cli",
      "note": "内测批次",
      "used": false,
      "used_by": null,
      "used_at": null,
      "expires_at": "2027-09-08T08:30:00.000Z"
    },
    {
      "code": "JT-ZZ99-XK7Q-M3PD",
      "created_at": "2026-09-08T08:30:00.000Z",
      "created_by": "offline-cli",
      "note": "",
      "used": true,
      "used_by": "p2p-client-001",
      "used_at": "2026-09-08T09:12:33.456Z"
    },
    {
      "code": "JT-QQ77-WW22-EE55",
      "created_at": "2026-09-08T08:30:00.000Z",
      "created_by": "offline-cli",
      "note": "",
      "used": false,
      "used_by": null,
      "used_at": null,
      "revoked": true,
      "revoked_by": "admin",
      "revoked_at": "2026-09-08T10:00:00.000Z",
      "revoked_reason": "渠道泄露"
    }
  ]
}
```

字段语义：

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | string | 激活码原文（规范格式，存储时已大写） |
| `created_at` | ISO 8601 | 生成时间 |
| `created_by` | string | 生成者（离线 CLI 为 `offline-cli`，网页后台为超管账号） |
| `note` | string | 批次备注，可空 |
| `used` | bool | **是否已消耗。true = 永久作废，不可再次使用** |
| `used_by` | string\|null | 消耗者标识（网站注册为用户名；P2P 侧为传入的使用者标识） |
| `used_at` | ISO 8601\|null | 消耗时间 |
| `revoked` | bool | **是否已被超管作废**（泄露处置等场景；可选字段，未作废的条目无此字段） |
| `revoked_by` | string | 作废操作者 |
| `revoked_at` | ISO 8601 | 作废时间 |
| `revoked_reason` | string | 作废原因，可空 |
| `expires_at` | ISO 8601\|null | **有效期截止时间**（v4 新增；`null`/缺省 = 永久有效。生成时由 `expiresDays`（0~3650 天，0=永久）推算写入） |

**消耗语义（关键约定）**：消耗 = 只把 `used:true / used_by / used_at` 写入该条目并写回磁盘，**绝不删除条目**，留痕排查。作废同理（写 `revoked:true` 系列字段，不删除条目）。

**状态优先级**：校验顺序为 `格式 → 存在 → 已用 → 已作废 → 已过期`；已使用的码**不可再作废**（使用记录优先保留），已作废未使用的码不可消耗；**已过期未使用的码同样不可消耗/注册**（`EXPIRED`，v4 起；码与记录保留在文件中）。

时间格式：ISO 8601 UTC（`new Date().toISOString()` 产出，带 `Z` 后缀、毫秒精度）。

## 4. 生成激活码（三个途径，均可离线）

### 4.1 离线 CLI（推荐用于 P2P 场景）

```bash
node server/scripts/generate-activation-codes.js [数量] [--note "备注"] [--expires 天数] [--out 文件.txt] [--file <路径>]

# 示例
node server/scripts/generate-activation-codes.js 10
node server/scripts/generate-activation-codes.js 5 --note "P2P内测批次" --out codes.txt
node server/scripts/generate-activation-codes.js 50 --expires 30 --file "D:\p2p分发\activation-codes.json"
```

- 单次 1~200 个；生成结果直接写入 `server/data/activation-codes.json`
- `--out codes.txt` 额外导出纯码列表文件（CRLF 行尾），方便线下发放
- `--expires N` 设置有效期 N 天（v4；省略或 0 = 永久有效，超出 1~3650 自动收敛），输出会逐码显示「有效期至」
- 该工具与网站后台共用同一文件与文件锁，可随时混用

### 4.2 超管网页后台 API（需要网站运行）

```
POST /api/admin/activation-codes/generate      # 仅 super_admin
GET  /api/admin/activation-codes               # 仅 super_admin，列表
```

请求体：`{"count": 10, "note": "P2P批次", "expiresDays": 30}`（`expiresDays` 可选，v4 起；0/缺省 = 永久有效）；成功响应：`{"success": true, "codes": ["JT-..."], "count": 10, "expiresAt": "2026-10-10T08:30:00.000Z", "message": "已生成 10 个激活码"}`（全部永久有效时无 `expiresAt` 字段）。

### 4.3 管理界面入口（封装 4.1/4.2，无需记命令）

- **网站后台「管理」页**（仅超管）：生成（可设有效期天数）/ 列表（总数/已用/未用/已作废/已过期 + 关键词与状态过滤）/ 作废 / **📋 复制未使用** / **⬇ 导出 CSV**（按当前筛选导出，v4）；未使用且 7 天内到期的码带「⚡ 即将过期」橙色标签
- **网页运维面板**（panel，默认 3457 端口）：同一套激活码管理（同样含复制未使用 / 导出 CSV / 即将过期标签，v4），走 panel 自身登录
- **本地维护脚本**（jingtu.bat / jingtu.ps1 菜单）：激活码生成/清单/作废快捷入口，内部调离线 CLI

## 5. 校验激活码（只读，不消耗）—— P2P 侧主要对接点

### 5.1 离线验码 CLI（场景 A）

```bash
node server/scripts/verify-activation-code.js <激活码> [激活码2 ...] [--json] [--file <路径>]
```

- 人读输出：`存储文件 / 每码状态 / 结论`
- `--json`：机器可读输出，P2P 安装脚本可直接解析：

```json
{
  "file": "D:\\...\\server\\data\\activation-codes.json",
  "results": [
    { "input": "JT-...", "code": "JT-...", "valid": true, "reason": null, "used": false, "used_by": null, "used_at": null, "revoked": false, "revoked_by": null, "revoked_at": null, "expired": false, "expires_at": null }
  ],
  "all_valid": true
}
```

- **退出码**：`0` = 全部可用；`1` = 存在无效码（格式错/不存在）；`2` = 存在已用码（无更严重问题时）；`4` = 存在已作废码（无更严重问题时）；`8` = 存在已过期码（v4 新增）

状态判定与网站后端完全一致：`INVALID_FORMAT`（格式错误）、`NOT_FOUND`（不在文件中）、`ALREADY_USED`（已消耗）、`REVOKED`（已作废）、`EXPIRED`（已过期，v4 起；人读输出会显示原有效期）。**校验是只读操作，不修改文件、不消耗码。**

### 5.2 自研只读校验（场景 B，任意语言）

按 §2 归一化 + §3 JSON 结构实现即可。推荐判定顺序：

1. 归一化后不匹配正则 → `INVALID_FORMAT`
2. 在 `codes` 数组中找不到 `code` 完全相等的条目 → `NOT_FOUND`
3. 条目 `used === true` → `ALREADY_USED`
4. 条目 `revoked === true` → `REVOKED`
5. 条目有 `expires_at` 且 `new Date(expires_at) <= Date.now()` → `EXPIRED`（v4）
6. 否则 → 可用

> 注意：文件可能正被其他进程写入。只读校验建议「读失败即重试」（间隔 ≥100ms，重试几次）；若要绝对稳妥，见 §8 的锁协议——P2P 侧读取时也可先取锁。

## 6. 消耗激活码（原子，一次性）

### 6.1 离线消耗 CLI（场景 A/B）

```bash
node server/scripts/consume-activation-code.js <激活码> <使用者标识> [--json] [--file <路径>]
```

- 语义与网站注册消耗完全相同：锁内「校验 → 标记 → 写回」，成功后该码永久作废
- `<使用者标识>` 写入 `used_by`，建议用 P2P 侧的用户名/设备号，便于对账
- **退出码**：`0` = 消耗成功；`1` = 无效（格式错/不存在）；`2` = 已被使用（响应里含 `used_by/used_at`）；`3` = 写入失败或锁超时（**码未消耗，可直接重试**）；`4` = 已被作废（响应里含 `revoked_by/revoked_at`）；`5` = 已过期（v4 新增，响应里含 `expired_at` 原有效期）
- `--json` 输出：`{"ok":true,"code":"JT-...","used_by":"p2p-client-001","used_at":"..."}` 或 `{"ok":false,"reason":"ALREADY_USED",...}` / `{"ok":false,"reason":"REVOKED",...}` / `{"ok":false,"reason":"EXPIRED","expired_at":"...","code":"JT-..."}`

### 6.2 Web 注册消耗（场景 C）

```
POST /api/auth/register
Content-Type: application/json
{ "username": "alice", "password": "Str0ngPass", "activationCode": "JT-AB2D-E3FG-H5JK" }
```

- 密码规则：≥8 位，须含小写 + 大写 + 数字
- 限流：同 IP/邮箱 15 分钟内最多 5 次注册请求
- 成功：`{"success": true, "user": {...}, "message": "注册成功"}`
- 失败（`{success:false, error:"...", code:"<REASON>"}`，HTTP 400）：

| code | 含义 |
|---|---|
| `INVALID_FORMAT` | 激活码格式不正确 |
| `NOT_FOUND` | 激活码无效（不存在） |
| `ALREADY_USED` | 激活码已被使用 |
| `REVOKED` | 激活码已被超管作废 |
| `EXPIRED` | 激活码已过有效期（v4 起；注册接口同样拦截过期码） |
| `USERNAME_TAKEN` | 用户名已被使用（HTTP 409；**此时码不会被消耗**） |

- **一致性保证**：若标记激活码写盘失败，网站会自动补偿删除刚建的账号，确保「码未消耗 ↔ 账号不存在」，不会出现白扣码。

## 7. 典型离线流程（推荐给 P2P）

```
① 超管离线生成
   node server/scripts/generate-activation-codes.js 50 --note "P2P首发" --expires 90
        → server/data/activation-codes.json（90 天有效期；省略 --expires = 永久）

② 分发
   将 activation-codes.json 部署到 P2P 机器（保持或告知路径）

③ P2P 用户注册时（P2P 软件内执行）
   验码（可选预检）：
     node server/scripts/verify-activation-code.js <用户输入的码> --json
   消耗：
     node server/scripts/consume-activation-code.js <用户输入的码> <p2p用户标识> --json
        → 退出码 0：建号放行；1/2/4/5：拒绝注册（2=已用、4=已作废、5=已过期）；3：提示重试

④ 对账（随时、离线）
   node server/scripts/list-activation-codes.js --status expired                      # 已过期码清单（v4）
   node server/scripts/list-activation-codes.js --status unused --out unused.txt   # 未消耗未作废码导出（含过期未用，可用 --status expired 单独剔除）
   node server/scripts/list-activation-codes.js --json                             # 全量统计（total/used/unused/revoked/expired）

⑤ 泄露处置（超管离线执行）
   node server/scripts/revoke-activation-code.js <泄露的码> <操作者> --reason "渠道泄露"
        → 该码即使未被使用也立即失效；已使用的码不可作废（使用记录保留）
```

多台 P2P 机器共享同一份文件时，**必须**让所有消耗都经由同一把锁（见 §8）——最简单的做法是所有机器通过共享磁盘使用同一份文件 + 统一使用本套 CLI 工具；或指定单一节点做消耗、其余节点做只读校验。

## 8. 并发文件锁协议（自研消耗方必读）

网站后端、生成 CLI、验码 CLI、消耗 CLI 全部走同一协议，任何绕过工具直接写文件的 P2P 实现都**必须**遵守，否则会出现双花（一码多用）：

1. 锁文件：`activation-codes.json.lock`（与数据文件同目录）
2. 加锁：以 **独占创建**（`open(..., 'wx')`）写锁文件；成功即持有
   - C++/C# 等价物：`CreateFile(..., CREATE_NEW, GENERIC_WRITE, FILE_SHARE_READ)` / `FileMode.CreateNew`
3. 锁内容：写入持有者 PID 与时间戳的 JSON：`{"pid":1234,"at":"2026-09-08T09:00:00.000Z"}`（自研方至少写入 PID，便于排查死锁残留）
4. 冲突处理：创建失败（已存在）→ 读取锁文件 mtime：
   - 距今 **< 5 秒**：视为他人持锁，等待 25ms 后重试，总等待 **10 秒**后放弃（报错，不写文件）
   - 距今 **≥ 5 秒**：视为死锁残留，删除锁文件后重新抢占
5. 写数据：**临时文件 + 原子改名**（写 `activation-codes.json.tmp.<pid>.<随机>` → `rename` 覆盖目标；Windows 上 rename 目标存在需先删或用 `MoveFileEx(MOVEFILE_REPLACE_EXISTING)`，失败可小睡 40ms 重试 3 次）
6. 解锁：删除锁文件（尽力而为）

**最简替代**：如果不想实现锁，请把所有「写文件」操作都收敛到本套 CLI 工具（它们已内置全部协议），P2P 自研部分只做只读校验。

## 10. FAQ

- **Q: 激活码能重复用吗？** 不能。消耗即写 `used:true` 永久作废，条目保留供对账。
- **Q: 码泄露了怎么办？** 用作废 CLI 处置：`node server/scripts/revoke-activation-code.js <码> <操作者> --reason "原因"`。已作废未使用的码任何人无法消耗；已使用的码不可作废（保留使用记录）。
- **Q: 码过期了还能用吗？** 不能（v4 起）。未消耗且已过期的码会被验码/消耗/注册统一拦截（`EXPIRED`），条目保留在文件中可对账；需要继续发放请生成新批次并用 `--expires` 设置合理有效期。
- **Q: 批次有效期设错了能改吗？** 当前没有改期/续期工具，`expires_at` 写入后不再变更。对账时用 `--status expired` 找出过期码即可——过期码本身已不可用，无需再作废。
- **Q: 文件被改坏了怎么办？** 服务层读取时会自动留存损坏现场副本（`*.corrupt-<时间戳>`），可从备份恢复后与留证副本比对，找出丢失/篡改的条目。
- **Q: 离线消耗时断电/崩溃会怎样？** 写入采用临时文件+原子改名，数据文件不会半截损坏；消耗失败时码未标记，可重试。
- **Q: P2P 能只把「未用的码」单独发给客户端本地校验吗？** 不建议——客户端不可信环境无法防止码被复制重放；推荐校验+消耗都在服务端/受控机器完成。
- **Q: 文件被删了怎么办？** 文件即数据库，请把 `activation-codes.json` 纳入常规备份（与网站其他数据一起）。

## 11. 在线推送同步端点（P2P → 网站，v3 新增）

除了离线导出文件（§7），P2P 本地生成的激活码还可以在**网站可达时**在线推送合并，两条通道互不冲突。

### 11.1 端点定义

```
POST /api/admin/activation-codes/sync
Content-Type: application/json
Cookie: <超管会话 Cookie>
X-CSRF-Token: <CSRF token>
```

- 权限：仅 `super_admin`（与 generate/list/revoke 一致）
- 请求体：`{"codes": [ <激活码条目对象>, ... ]}`，条目字段与 §3 数据文件格式完全一致；也接受纯字符串数组（自动按未知字段补齐）
- 单批上限：**500 个**（超过返回 `BATCH_TOO_LARGE`）

### 11.2 响应（扁平信封）

成功：

```json
{
  "success": true,
  "imported": ["JT-XXXX-XXXX-XXXX"],
  "skipped": ["JT-YYYY-YYYY-YYYY"],
  "invalid": [],
  "alreadySynced": false
}
```

失败：

```json
{ "success": false, "error": "codes 为空或格式非法", "code": "EMPTY_BATCH" }
```

| 字段 | 含义 |
|---|---|
| `imported` | 本次新导入的码（网站端此前不存在） |
| `skipped` | 已存在的码，原样跳过（幂等保证） |
| `invalid` | 格式非法被拒绝的码 |
| `alreadySynced` | `true` 表示本批全部已同步过（imported 为空） |
| `code` | 失败原因：`EMPTY_BATCH` / `BATCH_TOO_LARGE` / `NO_VALID_CODES` / `WRITE_FAILED` / `LOCK_TIMEOUT` / `FILE_CORRUPT` |

### 11.3 幂等与冲突规则

- **幂等合并**：码已存在（无论 used/revoked 与否）一律 `skipped`，不会覆盖网站端状态
- **去重建议**：P2P 侧维护同步记录（`activation-sync-state.json` 的 `syncedCodes`），推送成功后用响应 `imported` 回写，避免重复推送；即使重复推送也无副作用
- **导入走 `importCodes('p2p-sync')`**：与网站侧生成/消耗同一把文件锁，操作记入后台审计日志（操作人显示为「推送激活码（本地）」）

### 11.4 P2P 侧调用示例

见 P2P 仓库 `core/src/activation_codes.js` 的 `pushCodes(session)` 与 `pendingSyncCodes()` / `recordSyncResult()`；由 P2P GUI 的 `gui/main.js → syncActivationCodes()` 在超管登录/启动时自动调用（失败静默，下次再试）。P2P CLI 提供 `jingtu codes-pending` 查看待推送数量。

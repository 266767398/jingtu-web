## 2026-10-06 · 修复：布局根因修复收尾 + 全量失效缓存重载（?v=20261006e，SW v2.15）

现象：用户端（尤其有缓存的旧访客）首页与 VRC 页持续排版错乱，上轮版本戳提升到 `20261006c/d` 后部分客户端仍显示旧样式。

### 根因

1. 🔴 **SW cache-first 双锁**：`sw.js` 对带 `?v=` 的资源命中即返回，不请求服务器；即使 HTML 换了新戳，SW 旧缓存名不清理仍会命中旧副本。
2. 🔴 **HTTP immutable 强缓存**：`Cache-Control: public, max-age=31536000, immutable`，URL 不变即永不回源。
3. 🟡 **SW CACHE 名未提升**：上轮只升资源戳、未升 `CACHE` 名，SW 里旧资源无法被新版本驱逐。
4. 🟡 **h1/h2 媒体查询错位**：`.hero-overlay h2` 选择器写错，实际 DOM 为 `<h1 id="heroTitle">`，移动端 Hero 字号断点从未生效。
5. 🟢 **06-members.css 编码乱码**：约 50 处 GBK mojibake 中文注释，部分规则紧贴注释可能被解析吞掉。

### 改动

- `public/sw.js`：`CACHE = 'jingtu-v2.15'`（旧 `jingtu-v2.14` 整体被清理）。
- `public/css/03-layout.css`：两处 `.hero-overlay h2` → `.hero-overlay h1`（768/480 断点字号生效）。
- `public/css/99-design-system.css`：`.hero-overlay h2` → `.hero-overlay h1`（Hero 文字阴影生效）。
- `public/css/06-members.css`：修复全部 mojibake 注释，恢复可读。
- `public/js/group.js`：删除生产环境遗留 `console.log`。
- 版本戳提升为 `?v=20261006e`：`index.html` 中 `99-design-system.css`、`06-members.css`（2 处）、`loader.js`（懒加载 `group.js` 随其失效）；`style.css` 中 `03-layout.css` @import。
- `server/__tests__/security-regressions.test.js`：相关版本戳断言更新为 `20261006e`。

### 验证

- `npx jest`：49 suites / 871 tests 全部通过（含本批次新增断言）。
- 客户端需**硬刷新一次**（Ctrl+Shift+R）触发 SW 更新与缓存换新。

## 2026-10-06 · 构建修复：npm install exit 254 —— 恢复 builder 依赖清单拷贝（真根因）

现象：飞牛 NAS 构建在 `[builder] RUN npm install` 报
`process "/bin/sh -c npm install ..." did not complete successfully: exit code: 254`，
日志尾部无 npm 具体报错行。本机同参数（目录内含 package.json）安装正常（149 包）。

根因：对比提交历史发现 `53ce0c0`（内置 DaoCloud）误删了

报 `ENOENT`，在容器内以 254 退出。此前 `npm ci` 的 EUSAGE 也是同一根因——
并非「Docker git 上下文偶发 lockfile 未命中」。

### 修复

- `Dockerfile` builder 阶段在 `RUN npm install` 之前恢复
  `COPY server/package*.json ./`（依赖清单先行，保持层缓存；lockfile 存在时
  npm install 仍按锁版本精确安装）。

### 验证

- 空目录真跑同一命令 → `npm error code ENOENT ... Could not read package.json`（复现 254 根因）。
- 拷贝 `package*.json` 后同一命令 → exit 0，149 包，sharp/express 均装上。

## 2026-10-06 · 构建修复：npm ci 改 npm install，规避 Docker git 上下文「lockfile 未命中」

## 2026-10-06 · 生产优化：头像加载策略改为「直连优先、代理兜底」（VRCX 同款）

现象：部分头像在代理限速 / 回源超时 / 系统账号离线时**静默落到灰色占位**，`<img>` 永远不会
知道代理失败了，用户只能干等代理恢复，也没有任何备选路径绕过去。

### 根因

1. `server/routes/avatar.js` 的 `/proxy`（限速、回源失败无缓存）与 `/user`（缓存失败、
   系统账号未登录、限速、解析失败）失败时全部返回 **HTTP 200 占位 SVG**（`Cache-Control:
   no-store`）——`<img>` 的 `onerror` 只在 4xx/5xx 或网络错误时触发，**200 永远不会触发**，
   前端「代理失败 → 切直连 / 兜底」的既有逻辑形同虚设。
2. 全站头像全部走服务端代理：既绕不开服务端限速（CDN 全局令牌桶 200/min、每 IP 1000/min），
   也把「客户端本可以直连 CDN」的 VRCX 式路径完全堵死了——浏览器与服务器网络路径不同，
   客户端直连经常是通的。

### 修复（最终取向：直连优先、代理兜底）

- `server/routes/avatar.js`：新增 `sendPlaceholder(res)`——失败兜底统一返回 **502 占位 SVG**
  （`no-store`），语义 = 上游不可达，让 `<img>` 能感知失败触发 `onerror`；`/user` 5 处、
  `/proxy` 2 处失败路径全部改走它（不再返回 200 占位、不再被浏览器缓存）。
- `public/js/ui.js`（二期翻转默认取向）：
  - `proxyAvatar` 默认**直连优先**：`api.vrchat.cloud / api.vrchat.com / assets.vrchat.com`
    直接返回原始 CDN 直连地址（VRCX 同款）；后端已改写为 `/api/avatar/proxy?u=` 的地址同样
    反解回直连。`assets.amlcdn.com` 国内普遍被墙，保持代理优先（直连仅作失败兜底）。
  - `__avatarFail` 重试链：**直连失败 → 一次代理兜底**（服务端 L1/L2 缓存 + 多源回源），
    代理成功记入 `__avatarProxyCache`（15min TTL、上限 300 超限清空）→ 该 URL 转代理优先，
    避免反复直连超时；**代理失败（502）→ 反解直连一次**；两条路都失败才落默认占位 +
    60s 双 key（代理地址 + 直连地址）失败冷却，防 429 重试风暴。
  - 顶部导航栏 / 个人中心头像同步走 `proxyAvatar`，全站直连优先统一生效。
- 全站约 72 处 `<img>` 渲染点无需逐个改动——它们全部汇入全局 `__avatarFail`，一处升级全局生效。

### 验证

全量 Jest（49 套件 / 871 用例，含「直连优先、代理兜底」9 条回归）通过，ESLint 0 错误。

## 2026-10-06 · 生产修复：WS/地图/在线名单头像不显示（广播原始 CDN URL 被墙 + 地图 /user 兜底拼错 ID）

现象：群组列表 / 成员页 / 地图世界网格等 HTTP 展示面头像已正常，但**导航栏「在线成员」弹窗**、
**地图位置标记**与部分 **WS 实时消息**里的 VRChat 头像仍大量落到默认占位。

### 根因

1. `ws_service.js` 把 `users.vrchat_avatar_url`（原始 VRChat CDN 链接）直接广播进
   `online_users` / `location:update` / 群聊实时消息——国内网络直连 `api.vrchat.cloud` 与
   `assets.amlcdn.com` 在 TLS 层被阻断，前端 `<img>` 空等超时后只能 `__avatarFail` 落默认头像。
2. 地图位置标记（`map.js` `upsertLocationMarker` / `getMarkerPopup`）在头像为空或 amlcdn 时拼出
   `/api/avatar/user?u=<站内数字ID>`——该端点只接受 `usr_` 前缀的 VRChat ID，直接 400 → 默认头像。
3. `/api/users/all/locations` 未下发 `vrchatId`，前端无处取得正确的 VRChat ID。

### 修复

- `server/ws_service.js`：`onlineUsers` 入库时头像统一走 `proxyVrcAvatar()`（→ `/api/avatar/proxy?u=`），
  广播一律下发代理地址；同时把 `vrchat_id AS vrchatId` 带入 `onlineUsers`、`online_users` 名单与
  `location:update` 负载，供前端做按 ID 兜底。
- `server/routes/users.js` `/api/users/all/locations`：补下发 `vrchatId`。
- `public/js/map.js`：地图标记/气泡的 `/api/avatar/user` 兜底改用 `userData.vrchatId`（对齐
  `mapAvatarSrc(url, uid)` 的 usr_ 前缀契约），空头像且无 vrchatId 时自然落默认头像。
- `public/js/main.js` 在线成员弹窗：对齐成员页同一套头像链——服务端代理地址直用；
  amlcdn 历史缩略图或空值时走 `/api/avatar/user?u=<vrchatId>`，再不行才默认占位。

### 验证

全量 Jest（49 套件 / 861 用例，ws-service / module-regressions 均在）通过，ESLint 0 错误。

## 2026-10-06 · 生产修复：Docker/容器环境「运维面板」启动不了（点按钮空等 10s 弹「启动失败」）

## 2026-10-06 · 生产修复：数据库关闭时报错（关库瞬间 ECONNREFUSED / Pool is closed + MySQL 被 SIGKILL）

现象：`docker stop` / 停库时，MySQL 日志止于 `Received SHUTDOWN from user <via user signal>`，
应用侧同时刷出连接类报错（`ECONNREFUSED` / `Pool is closed`）与部分 500；
MySQL 若在默认 10s 宽限内未完成 InnoDB 冲刷还会被 SIGKILL（容器退出码 137，显示为「报错」）。

### 根因

1. 优雅关闭顺序缺陷（`server.js`）：先 `pool.end()` 关连接池、后取消定时任务——关闭窗口内
   node-schedule 定时任务与 `tasks.js` 的 CronJob 会打到已关闭的连接池（`schedule.gracefulShutdown()`
   本应更早，`tasks.stopTasks()` 从未被调用）；同时 `server.close()` 不 await、不排空在途请求。
2. 数据库心跳（`db.js` 15s）没有关闭开关：`pool.end()` 之后若心跳触发，会 `recreatePool()` 又建新池。
3. `unhandledRejection` 的致命分支把 `ECONNREFUSED` 等连接错误判为进程损坏 → `exit(1)` 触发重启，
   叠加在错误日志之上表现为「反复退出/重启」。
4. Docker 两个 compose 均未设 `stop_grace_period`（默认 10s）：MySQL 8 关库需冲刷 InnoDB 缓冲，
   大库超 10s 就被 SIGKILL → 容器退出码 137。

### 修复

- `server/server.js` gracefulShutdown 重排为：① `_isShuttingDown = true` + `dbMod.setDbShuttingDown(true)`
  （进程级/连接池双重关闭标志——置位后 `uncaughtException`/`unhandledRejection` 不再把关闭途中
  的连接类错误判为进程损坏而 `exit(1)`）
  → ② `startSchedule.gracefulShutdown()` + `tasks.stopTasks()`（先停定时任务，杜绝打到已关的池）
  → ③ 停 CSRF 清理/WS → ④ await `server.close()` 排空在途 HTTP（上限 5s，长连接/流式响应超时强放）
  → ⑤ `pool.end()` → ⑥ `cache.closeCache()` → ⑦ `exit(0)`。
- `server/db.js`：新增 `setDbShuttingDown` 关闭开关——置位后心跳跳过、`recreatePool()` 不再重建，
  杜绝「pool.end() 之后又 new 一个池」的竞态。
- `docker-compose.yml` / `docker-compose.fnos.yml`：db 与 app 均加 `stop_grace_period: 30s`，
  让 MySQL 关库与应用优雅关闭有充足宽限，不再被 SIGKILL（退出码 137）。

### 说明（本次日志本身）

用户贴出的 MySQL 日志中 `CA certificate ca.pem is self signed`、`Insecure configuration for --pid-file`
均属 MySQL 8 常规 Warning（非错误）；`Received SHUTDOWN` 是收到停机信号后的正常第一行——
此前日志截断于此，若后续没有 `Shutdown complete` 且容器显示 error，即为上文第 4 点被 SIGKILL 所致，
本修复后该场景消失。

关闭守卫断言），ESLint（server.js / db.js）0 错误 0 警告。

## 2026-10-03 · VRChat API 实测（连通性/风险/选型结论）

- 实测链路全部通过：上游 `api.vrchat.cloud/api/1/config` → HTTP 200；项目 `server/vrc.js` 封装层
  `/config`、`/time` → 均 200；本地 `/api/health` → 200；`/api/vrc-monitor` 未登录 → 401（守卫正常）。
- 风险结论：政策红线（Tupper Policy：禁 avatar ripping/客户端修改/自动化刷接口）、接口随时破坏性变更、
  账号风控、cookie 隐私均已由内置 40/min 限流、moderation 仅人工触发、写操作限本人绑定 cookie 覆盖。
- 选型结论：**代码层维持手写 `server/vrc.js`**（限流/安全/多账号定制均在），**参考层用官方 OpenAPI**
  （`ai-scratch/vrcapi-spec/` 作权威说明书）；不建议引入官方 npm SDK（会丢失限流与安全层）。

# 境途同游 Web 项目 — 部署与运维指南

> 版本：V8.2  
> 最后核对：2026-10-01  
> 本文以当前 `server/package.json`、`server/package-lock.json`、服务入口、路由和启动脚本为准。

## 一、实际运行要求

### 1.1 软件与服务

| 项目 | 实际要求 | 说明 |
|---|---|---|
| Node.js | **20.9.0+** | 锁定的生产依赖 `sharp@0.35.3` 要求 Node `>=20.9.0`；Node 18 已不满足当前依赖树。**SQLite 模式还需 Node ≥22（`node:sqlite` 内置模块），推荐 23.x** |
| npm | 随 Node 20 提供的当前版本 | 使用 `server/package-lock.json` 执行 `npm ci` |
| MySQL | **5.7+ 或 8.0+**（默认模式必需） | 代码使用 JSON 列及 `JSON_EXTRACT`；入口注释和 Windows 脚本仍以 5.7 为基线，MySQL 8 也兼容。**可选 SQLite 模式**（`JINGTU_DB_ENGINE=sqlite`）则无需 MySQL，改用 Node 内置 SQLite（见 §2.4） |
| Redis | 可选，配置 `REDIS_HOST` 即启用 | 服务入口已调用 `cache.initCache()`（`server.js`）：配置 `REDIS_HOST` 后 CSRF token 与接口限流计数升级为 Redis 共享态；未配置/连接失败自动回退进程内实现 |
| PM2 / Nginx / TLS | 仓库外部建议 | 仓库自带 `ecosystem.config.js`（单实例 fork、指数退避、PM2 日志落盘），推荐 `pm2 start ecosystem.config.js`；Nginx/证书自动化仍按运行环境另行安装和维护 |

MySQL 是**默认模式**可用业务服务的必要条件。当前入口在数据库初始化失败时仍会监听 HTTP 端口，以便进行 setup；这不表示应用可在无数据库状态下正常工作。应以 `/api/health/ready` 为就绪标准，而不是只检查端口。SQLite 模式不依赖外部 MySQL，仍建议用 `/api/health/ready` 校验存储可写。

### 1.2 目录约定

以下示例假定仓库位于 `/srv/jingtu-web`：

```text
/srv/jingtu-web/
├── .env                  # 服务实际读取的环境文件
├── public/
├── uploads/
├── backups/
├── logs/
└── server/
    ├── package.json
    ├── package-lock.json
    └── server.js
```

依赖安装目录和 Node 启动工作目录都是 `server/`，但 `.env` 位于仓库根目录。`swagger.js` 使用相对路径扫描 `./routes/*.js`，因此从 `server/` 启动还能确保 API 注释被正确发现。

## 二、推荐的手动安装

### 2.1 获取代码并安装依赖

```bash
git clone <实际仓库地址> /srv/jingtu-web
cd /srv/jingtu-web/server
npm ci
```

当前已支持 `npm ci --omit=dev`：自 V7.10 起 `server.js` **默认任何环境都不加载 Swagger**（P2-169 起改为显式开关），仅当 `.env` 设置 `ENABLE_SWAGGER=1` 才 lazy 加载，且文档访问要求超级管理员登录；而 `swagger-jsdoc` / `swagger-ui-express` 仍列在 `devDependencies`。生产部署可省略开发依赖以减小体积；本地开发与测试仍需完整安装。若确实需要在生产查看 API 文档，应开启 `ENABLE_SWAGGER=1` 并用超级管理员账号访问（见第八节与 `deploy/nginx/jingtu.conf`）。

### 2.2 创建数据库与账号

```sql
CREATE DATABASE jingtu_group
  CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'jingtu_user'@'127.0.0.1' IDENTIFIED BY '替换为强密码';
GRANT ALL PRIVILEGES ON jingtu_group.* TO 'jingtu_user'@'127.0.0.1';
FLUSH PRIVILEGES;
```

若让 `db_init.js` 自动创建数据库，连接账号还必须具有建库权限；生产环境更建议由 DBA 预建数据库，再只授予该库所需权限。不要把 MySQL 端口暴露到公网。

### 2.3 配置根目录 `.env`

```bash
cd /srv/jingtu-web
umask 077
cat > .env <<'EOF'
MYSQL_HOST=127.0.0.1
MYSQL_PORT=3306
MYSQL_USER=jingtu_user
MYSQL_PASSWORD=替换为数据库强密码
MYSQL_DATABASE=jingtu_group

NODE_ENV=production
PORT=3456
CORS_ORIGINS=https://jingtu.example.com
# 经 Nginx/宝塔/反代部署必须显式设置（否则 req.ip 坍缩为 127.0.0.1，限流/告警失真）
TRUST_PROXY=1

SESSION_SECRET=替换为至少32字节的持久随机值
ENCRYPT_KEY=替换为64位十六进制字符串
# 生产必须设为真实域名（邮件内重置/通知链接、sitemap 基址；留空回退 http://localhost:3456）
APP_URL=https://jingtu.example.com
# 数据库恢复接口口令（随机 ≥32 字节 hex；留空则 /api/system/db-recover 写接口 503 安全默认）
RECOVERY_TOKEN=替换为随机生成的持久令牌

GROUP_ID=替换为实际群组ID
VRC_API_KEY=替换为实际密钥
LOG_LEVEL=INFO
EOF
chmod 600 .env
```

> **域名说明**：当前本地开发环境域名为 `http://localhost:3456`（与 `.env` 的 `PORT=3456` 一致）；上表及下文 `jingtu.example.com` 均为**部署到宝塔/生产时替换的真实域名模板**。另：`sitemap` 基址 `SITEMAP_BASE_URL` 与邮件重置链接 `APP_URL` 代码默认均为 `http://localhost:3456`（`server/mailer.js`、`server/routes/sitemap.js`），生产须显式设为真实域名，否则生成的 sitemap / 邮件链接地址错误（详见 `docs/03` 环境变量表）。

生成持久密钥：

```bash
openssl rand -hex 32   # 可用作 SESSION_SECRET
openssl rand -hex 32   # 64 位十六进制，可用作 ENCRYPT_KEY
```

`SESSION_SECRET` 和 `ENCRYPT_KEY` 缺失时，代码会生成临时值以支持初始化，但重启后会改变，导致会话失效或已加密数据无法解密。生产环境必须持久保存并纳入受控的密钥备份/轮换流程。

可选 SMTP 配置使用 `SMTP_HOST`、`SMTP_PORT`、`SMTP_USER`、`SMTP_PASS`、`SMTP_SECURE` 和 `SMTP_FROM`。社交链接的当前键名是 `VRC_GROUP_URL`、`KOOK_URL`、`OOPZ_URL`。

#### VRChat 系统账号自动重登（可选）

当部署环境的公网出口 IP 与 VRChat authToken 签发时的 IP 不一致时，VRChat Pipeline 会在握手后返回 `err` 帧并断开（WebSocket 1006）。为保证这类故障自动恢复，可在**管理面板「系统 VRChat 账号」卡片**中保存系统账号凭据：

- 必填：VRChat 用户名与密码（表单保存后经 `ENCRYPT_KEY`（AES-256-GCM）加密后写入 `server/session.json` 的 `credentials` 字段，**明文不会落盘**；`ENCRYPT_KEY` 变更后需重新保存）；
- 可选：TOTP 密钥（两步验证时由服务端在后台自动完成，无需人工干预）；
- 保存成功后，「自动重登未配置」状态变为「自动重登已配置」。

机制：Pipeline 连接被服务端拒绝（`err` 帧 + 1006）时，系统会**暂停重连风暴**，仅输出一条告警日志；随后自动使用已保存的账号凭据重新登录（必要时以 TOTP 完成两步验证），成功后轮换 authToken 并恢复连接。凭据缺失、仅支持邮箱验证码/OTP 等无法自动完成的两步验证场景，将保持暂停并等待人工处理。当前状态可通过 `GET /api/vrc-credentials-status` 或 `/api/health` 的 `vrcAutoReloginConfigured`、`pipeline.sessionRejected` 字段观测（详见 `docs/05` §3.2）。

**自动重登防封禁双护栏（2026-09-25，F-30）**：为避免高频自动重登触发 VRChat 风控/封号，自动重登带两层护栏——① **最小间隔钳制**：两次自动重登至少间隔 60 秒（`RELOGIN_MIN_INTERVAL_MS`），杜绝连发风暴；② **连败指数退避**：自动重登连续失败后按 `5min × 3^(失败次数-1)` 递增等待，封顶 30 分钟（1 败→5min、2 败→15min、3 败及以上→30min）；成功清零失败计数，`BACKOFF/NO_CREDENTIALS` 不计失败。熔断期间状态经 `/api/health` 的 `vrcAutoRelogin`（`failStreak/backoffUntil/backoffRemainingSec/lastResult`）暴露，管理面板在连败 >0 时显示 🛡️ 橙色告警横幅。**防泄露说明**：凭据解密失败时系统**只告警、不清除、不写回**（保留原加密串，由管理面板重新保存覆盖）——避免跨环境共享 `session.json` 时（如不同 `ENCRYPT_KEY`）误删生产凭据。⚠️ 当前实例 `server/session.json` 系统账号凭据为空，**请到管理面板「系统 VRChat 账号」卡片重新保存账号密码**。

### 2.4 初始化与启动

```bash
cd /srv/jingtu-web/server
node db_init.js
npm start
```

`npm start` 等价于 `node server.js`。入口启动时也会执行 `db_init.js`，创建缺失表并应用当前迁移；显式先运行一次可在正式启动前看到初始化错误。

**SQLite 模式（无需 MySQL）**：

```bash
cd /srv/jingtu-web/server
JINGTU_DB_ENGINE=sqlite node db_init.js      # 初始化 server/data/jingtu.sqlite（自动建目录）
JINGTU_DB_ENGINE=sqlite npm start            # 启动（Session 回退 MemoryStore）
```

库文件路径可用 `JINGTU_SQLITE_PATH` 覆盖；SQLite 模式忽略 `MYSQL_*`。启动时 `express-mysql-session` 会尝试连接 MySQL 失败后回退 MemoryStore（日志出现连接失败属预期）。

创建运行目录并赋予服务账号写权限：

```bash
cd /srv/jingtu-web
mkdir -p uploads backups logs
chown -R jingtu:jingtu uploads backups logs
chmod 750 uploads backups logs
```

不要递归地把整个仓库交给 Web 服务账号写入。

### 2.5 建站向导的实际限制

浏览器页面是 `/setup.html`，API 是 `/api/setup/*`。向导保存配置时要求目标数据库中已经存在 `users` 表；它不会创建表。若确需使用向导，可在根目录尚无 `.env` 时先用进程环境初始化：

```bash
cd /srv/jingtu-web/server
MYSQL_HOST=127.0.0.1 \
MYSQL_PORT=3306 \
MYSQL_USER=jingtu_user \
MYSQL_PASSWORD='数据库密码' \
MYSQL_DATABASE=jingtu_group \
node db_init.js

node server.js
# 然后访问 http://127.0.0.1:3456/setup.html
```

向导生成 `.env` 后应重启服务，并立即执行生产安全检查。公网部署时不要长期暴露未完成的 setup 实例。

## 三、仓库脚本的准确用法与限制

### 3.1 `install.sh`

`install.sh` 现已改为可用的部署脚本（改进版），覆盖宝塔与裸机：

- 支持在**已克隆的项目目录内**直接部署（检测到 `server/server.js` 即跳过克隆），或按 `REPO_URL` 克隆到 `/www/wwwroot`。
- 检测 Node.js：版本低于 20 时在 Debian/Ubuntu 自动通过 NodeSource 安装 20.x；也可改用宝塔 Node 版本管理器。
- 依赖安装优先 `npm ci`（有锁文件），否则 `npm install`。
- 生成根目录 `.env`，密钥（`SESSION_SECRET` / `ENCRYPT_KEY`）未提供时自动随机生成并设权限 `600`。
- 提供 `MYSQL_ROOT_PASSWORD` 时用本地 `mysql` 客户端创建数据库与账号；否则提示在宝塔手动创建。
- 执行 `db_init.js` 建表/迁移；生成 `ecosystem.config.js`（PM2）并启动，未装 pm2 时退化为 `nohup` 后台启动。
- 生成 `deploy/nginx/jingtu.conf` 反向代理模板，并在结尾给出宝塔「网站/反向代理/SSL」的后续步骤。

非交互用法：

```bash
REPO_URL=https://github.com/你的名/jingtu-web.git \
DOMAIN=jingtu.example.com DB_NAME=jingtu_group DB_USER=jingtu_user \
DB_PASS='强密码' MYSQL_ROOT_PASSWORD='root强密码' \
bash install.sh
```

完整参数与故障排查见仓库根目录 `DEPLOY.md`。

### 3.2 Linux/宝塔启动脚本 start-services.sh

仓库根目录的 `start-services.sh` 是 Linux/宝塔数字菜单版启动脚本（拉 MySQL 服务 → 启动 Nginx → 启动 Node），含健康检查与进程探测。其健康检查请求 `/api/health`——该端点自 2026-09 起已存在（`server.js`，返回 VRChat 系统状态与管道健康），脚本按 200 判定可正常通过；通用监控仍建议使用第五节 `/api/health/ready` 与 `/api/health/live`。脚本最后输出 “All services started” 不应作为生产就绪判据，生产请按实际路径、端口与健康端点维护。

### 3.2.1 站点重启/运维脚本 `jingtu.ps1`（2026-08-27 加固）

仓库根的 `jingtu.bat` → `jingtu.ps1` 是 Windows 下「停止/启动/重启」站点的实际运维脚本（含 MySQL 服务优先级、Nginx 80、Node 3456、`Test-Port` IPv6 匹配、`$NoBrowser` 守卫等）。2026-08-27 修复一处**此前未暴露的关键崩溃**：

- **现象**：干净的 `restart` 跑到 `Start-Nginx`/`Start-Site`（内部用 `Start-Process -RedirectStandard*`）时崩溃，报 `System.ArgumentException: 已添加项。字典中的关键字:"Path" 所添加的关键字:"PATH"`。
- **根因**：宿主 PowerShell 环境块里存在大小写重复的变量（`Path`/`PATH`/`path` 三套），`Start-Process -Redirect*` 在构建子进程环境字典（大小写不敏感的 `StringDictionary`）时撞键抛异常。旧版 restart 总在 MySQL 步骤挂掉、站点一直手动拉起，故从未触发。
- **修复**：新增纯 PowerShell 的 `Repair-Environment` 函数并在入口调用——用已合并（大小写不敏感）的环境变量名枚举，对每个变量先 `while` 删光所有大小写变体再 set 一次（带 32 次上限防死循环），单变量 `try/catch` 兜底「值过长」。`Add-Type`（C# P/Invoke）方案因被沙箱拦截且在子进程挂死，已彻底弃用。
- 验证：`jingtu.ps1 restart` 端到端跑通（停旧站 → 拉 MySQL 服务 → 起 Nginx → `Start-Process -Redirect` 起 Node），EXIT=0，无残留进程。

**激活码管理菜单（`[A]`，2026-09 新增）**：`jingtu.ps1` 主菜单新增 `[A] 激活码管理` 入口。纯 PowerShell 实现，离线可用（不依赖 MySQL / Node），直接操作激活码离线存储文件（默认 `server\data\activation-codes.json`，可用环境变量 `ACTIVATION_CODES_FILE` 覆盖）：

| 子项 | 功能 |
|---|---|
| `[1]` 查看激活码清单 | 过滤：`[1]`全部 / `[2]`未使用 / `[3]`已使用 / `[4]`已作废 |
| `[2]` 生成激活码 | 数量 1-200（默认 10），可选备注；有效期 `expiresDays` 0-3650 天（0=永久） |
| `[3]` 验证激活码 | 校验单码有效性（未使用 / 未作废 / 未过期） |
| `[4]` 作废激活码 | 可选作废原因 |
| `[5]` 激活码存储位置 | 显示存储文件路径 |
| `[0]` 返回主菜单 | — |

> 命令行批量操作可用 `server/scripts/` 下的 5 个 CLI：`generate-activation-codes.js` / `list-activation-codes.js` / `verify-activation-code.js` / `revoke-activation-code.js` / `consume-activation-code.js`；网页端管理入口见运维面板「激活码」页签与主站 `/api/admin/activation-codes/*`（详见 25-激活码离线对接说明-P2P联动.md）。

> 注意：本节所述脚本均为仓库辅助启动/运维用途；生产环境不应依赖硬编码路径与端口，除非已按实际环境维护。

### 3.2.2 建站引导（初始化向导）加固（2026-08-27）

- `server/routes/auth.js` 的 `POST /api/auth/init` 修复**静默轮换加密键 footgun**：原逻辑先自动生成 `.env`（含随机 `ENCRYPT_KEY`）再查超管是否已存在；若超管已存在也会重生成键、导致存量数据无法解密。改为**先查超管存在性，再决定是否生成 `.env`**。
- `server/routes/setup.js` 的 `POST /api/setup/save` 新增**后端密钥强度校验**：`ENCRYPT_KEY` 要求 HEX64、`SESSION_SECRET` ≥32 字符，不合法时回落到现有值或 crypto 随机生成，不再静默接受弱密钥。

### 3.3 仓库治理（AI 临时脚本与 Docker 上下文）

为保持仓库可维护、避免把一次性排查脚本打进 Docker 镜像或误提交，所有由 AI 辅助生成的一次性脚本（`check_*.py`、`fix_*.py`、`search_*.py`、`debug_*.js` 等）与临时探针（`scripts/_*.js`，含 `_inject-geo-bug.js` 这类注入测试脚本）已统一移动到仓库根的 `ai-scratch/` 目录，并从版本控制与 Docker 构建上下文中排除：

- `.gitignore` 增加 `ai-scratch/`、`logs/`、`backups/`；
- `.dockerignore` 增加 `ai-scratch/`。

`server/` 目录现仅保留运行所需源码（约 25 个 `.js`/`.py`），Docker 构建上下文不再包含无关脚本，镜像更小、也更不易泄露调试期可能硬编码的凭证。

> 2026-10-01 整理：`ai-scratch/` 目录（约 400+ 一次性脚本/输出）已整体删除（非版本控制内容，`git status` 从未跟踪）；需要时须凭提交历史或旧副本找回。

### 3.4 本版已修复的安全/部署问题

- **Swagger 默认不加载**：`server.js` 不再无条件 `require('./swagger')`，也不按 `NODE_ENV` 判断——仅 `ENABLE_SWAGGER=1` 显式开启且文档访问要求超级管理员登录（P2-169），生产可用 `npm ci --omit=dev`。
- **`trust proxy` 已设置**：由 `TRUST_PROXY` 控制。代码安全默认为「未设置/留空 ⇒ `false`（不信任任何代理，含生产）」，经反向代理部署时必须显式设置（如 `TRUST_PROXY=1` 或实际跳数），反向代理后的 `req.ip`、限流、登录失败/IP 告警才会恢复正确。
- **Session Cookie `secure` 改 `auto`**：配合 `trust proxy` 由 `req.secure` 决定，经 HTTPS 才自动加 `Secure`。
- **WAF 路径检测改为根路径段匹配**：不再用 `url.includes('/system')` 这类子串匹配，避免误伤 `/api/admin/analytics/system` 等合法嵌套路由（此前会被 404）。
- **上传魔数校验已接入**：通过 `utils.secureUpload` 包装器覆盖全部 8 个上传路由（`album/chat/live/posts/profile/users`），扩展名合法但内容不符的伪装文件会被拒绝。
- 详见 `docs/09-已知问题与技术债务.md`。

## 四、进程与反向代理（外部建议）

### 4.1 PM2 单实例

仓库自带 `ecosystem.config.js`（单实例 fork、cwd 指向 `server/`、指数退避重启、PM2 日志落盘 `logs/pm2-out.log`），推荐直接使用；如手工启动 PM2，必须显式设置工作目录，并保持单实例：

```bash
pm2 start server.js \
  --name jingtu-web \
  --cwd /srv/jingtu-web/server \
  --instances 1
pm2 save
pm2 startup
```

常用命令：

```bash
pm2 status
pm2 logs jingtu-web --lines 100
pm2 restart jingtu-web
pm2 stop jingtu-web
pm2 delete jingtu-web
```

**不要假定支持 cluster。** WebSocket 用户映射、在线状态和部分 VRChat pipeline 状态仍保存在进程内存中，共享文件存储与 WS 粘性方案也未落地；未完成这些之前，不要使用 `-i max` 或多副本负载均衡。

> 2026-09-12 补充：配置 `REDIS_HOST`（可选 `REDIS_PORT/REDIS_PASSWORD/REDIS_DB`，`.env.example` 与 `docker.env.example` 均已列出，Docker 侧 `docker-compose.yml` 已透传）后，**CSRF token 与接口限流计数**已升级为 Redis 共享态（未配置时自动回退本地实现，行为不变），`ecosystem.config.js` 的 `instances: 1` 锁仍是刻意设置——上面对 WS/pipeline/文件存储的限制尚未解除。

也可使用 systemd 等替代 PM2；PM2 不是应用依赖。

### 4.2 Nginx 与 TLS

Nginx、Certbot 和证书续期均是外部运维建议，不由仓库安装。仓库已提供可直接使用的模板 `deploy/nginx/jingtu.conf`（含 WebSocket 升级 map 联动、500m 上传体——对齐相册 500MB 单文件上限、以及生产屏蔽 `/api-docs` 的片段），可整体替换进宝塔「网站 → 设置 → 配置文件」，或作为独立 `conf.d` 引入。最小反向代理示例：

```nginx
# Upgrade 头联动（P2-91）：仅真实 WebSocket 握手打 upgrade，普通 HTTP 保持 close，
# 避免硬编码 Connection "upgrade" 破坏 keep-alive
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

server {
    listen 80;
    server_name jingtu.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;
    server_name jingtu.example.com;

    ssl_certificate     /etc/letsencrypt/live/jingtu.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/jingtu.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    # 与相册单文件 500MB 上限对齐（P2-76）；低于此值大图/视频上传会在反代层 413
    client_max_body_size 500m;

    # 生产环境屏蔽公开的 API 文档（避免泄露接口结构）
    location = /api-docs.json { return 404; }
    location ^~ /api-docs { return 404; }

    location / {
        proxy_pass http://127.0.0.1:3456;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 120s;
    }
}
```

验证并重载：

```bash
nginx -t
systemctl reload nginx
curl -fsS https://jingtu.example.com/api/health/live
curl -fsS https://jingtu.example.com/api/health/ready
```

自 V7.10 起，应用已修正反向代理相关两项，使反向代理上线后行为正确：

1. **`trust proxy`**：新增 `app.set('trust proxy', …)`，由 `TRUST_PROXY` 环境变量控制。**未设置/留空一律为 `false`（含生产）**——这是防伪造 `X-Forwarded-For` 的安全默认；经反代部署必须显式设 `1`（或实际跳数，`true`/`1` 等价于信任第一跳），直暴露公网保持不设置或 `false`/`0`。仅信任实际代理层，才能确保 `req.ip`、限流和安全告警不会被伪造或聚合到代理 IP。
2. **Session Cookie `secure`**：由原先错误依赖 `MYSQL_HOST` 是否含 `127.0.0.1`，改为 `'auto'`——当请求经 HTTPS（`req.secure`，依赖上面的 `trust proxy` 解析 `X-Forwarded-Proto`）时自动加 `Secure`，纯 HTTP 则不加。

上线前仍必须验证：生产 Session Cookie 始终带 `Secure; HttpOnly; SameSite=Lax`；HTTP 全部跳转 HTTPS；HSTS 仅在完成全站 HTTPS 后启用。仅配置 Nginx 头不能替代上述应用检查。

## 五、健康检查、端口与日志

### 5.1 正确健康端点

```bash
# 存活：只证明 Node 进程能响应
curl -fsS http://127.0.0.1:3456/api/health/live

# 就绪：同时执行 SELECT 1，数据库不可用时返回 503
curl -fsS http://127.0.0.1:3456/api/health/ready

# 详细状态：需要管理员登录会话
# GET /api/health/detailed
```

存在通用 `GET /api/health`（`server.js`，返回 VRChat 系统状态与管道健康），可用于快速探活；监控和滚动发布建议使用 `/api/health/ready`（就绪/依赖检查）；存活探针使用 `/api/health/live`。

### 5.2 检查端口

Linux：

```bash
ss -ltnp | grep -E ':(80|443|3306|3456)\b'
lsof -nP -iTCP:3456 -sTCP:LISTEN
```

Windows PowerShell：

```powershell
Get-NetTCPConnection -State Listen -LocalPort 80,3306,3456
Get-Process -Id (Get-NetTCPConnection -State Listen -LocalPort 3456).OwningProcess
```

不要用 `kill -9` 或按进程名批量终止作为常规释放端口方式；先识别 PID，再优雅停止对应服务。

### 5.3 日志

应用日志模块写入仓库根目录 `logs/`，单文件超过 10 MB 时轮转并保留 5 个历史文件。PM2/Nginx 日志位置由各自外部配置决定，不应假定仓库已有 PM2 日志轮转配置。

```bash
tail -F /srv/jingtu-web/logs/app.log
pm2 logs jingtu-web --lines 100
journalctl -u nginx --since today
```

## 六、数据库、备份与恢复

### 6.1 MySQL 配置注意事项

可按主机内存和负载调优 InnoDB、连接数和慢查询日志，但应先在测试环境验证。例如：

```ini
[mysqld]
character-set-server = utf8mb4
collation-server = utf8mb4_unicode_ci
slow_query_log = 1
long_query_time = 2
```

**MySQL 8 已移除 Query Cache。** 不要在 MySQL 8 配置中加入 `query_cache_type` 或 `query_cache_size`；未知变量可能使 MySQL 无法启动。即使使用 MySQL 5.7，也不建议为本项目假定开启 Query Cache。

### 6.2 手动备份

避免把密码直接写进命令行或 crontab。使用权限为 `600` 的 MySQL option file：

```ini
# /etc/jingtu/mysql-backup.cnf
[client]
host=127.0.0.1
port=3306
user=jingtu_user
password=替换为数据库密码
```

```bash
chmod 600 /etc/jingtu/mysql-backup.cnf
mkdir -p /srv/jingtu-web/backups
mysqldump \
  --defaults-extra-file=/etc/jingtu/mysql-backup.cnf \
  --single-transaction --routines --triggers \
  jingtu_group \
  > /srv/jingtu-web/backups/jingtu_group_$(date +%Y%m%d_%H%M%S).sql
```

服务入口已调用 `tasks.startTasks()`（`server.js`），**每日自动备份与保留策略已启用**：每日 02:30（Asia/Shanghai）自动备份，FILE/NOTIFICATION/BACKUP_RETENTION_DAYS 控制清理保留天数；自动备份要求 `mysqldump` 在服务进程的 `PATH` 中（容器/宝塔环境请确认），管理路由亦可按需手动创建备份。

生产备份必须同时覆盖：

- MySQL 数据；
- `uploads/` 等用户文件；
- 恢复所需配置与密钥（加密、最小权限存储，不能进入源码仓库）；
- 异机/异地副本、保留策略、监控告警和定期恢复演练。

### 6.3 CLI 恢复

先停写/停服并备份当前状态，再恢复：

```bash
pm2 stop jingtu-web

mysqldump \
  --defaults-extra-file=/etc/jingtu/mysql-backup.cnf \
  --single-transaction jingtu_group \
  > /srv/jingtu-web/backups/pre_restore_$(date +%Y%m%d_%H%M%S).sql

mysql \
  --defaults-extra-file=/etc/jingtu/mysql-backup.cnf \
  jingtu_group \
  < /srv/jingtu-web/backups/jingtu_group_20260809_030000.sql

pm2 start jingtu-web
curl -fsS http://127.0.0.1:3456/api/health/ready
```

### 6.4 内置备份 API

实际路由均需要管理员会话，修改操作还受全局 CSRF 检查约束：

```text
GET    /api/admin/backups
POST   /api/admin/backups/create
POST   /api/admin/backups/restore/:filename
DELETE /api/admin/backups/:filename
POST   /api/admin/backups/cleanup
GET    /api/admin/backups/:filename/download
```

恢复端点不是 `/api/backups/restore/{filename}`。文件只从根目录 `backups/` 读取，且服务主机必须能从 `PATH` 找到 `mysql` 客户端。恢复属于高风险操作，应先维护窗口停写、生成恢复前备份，并在完成后检查就绪、关键数据和日志。

## 七、Redis 的当前状态

`redis@6.1.0` 是已安装的 Node 客户端依赖，它要求 Node 20+；这不等于要求 Redis Server 6.1。服务入口已调用 `cache.initCache()`（`server.js`）——**配置 `REDIS_HOST` 后即启用**：CSRF token 存储与接口限流计数升级为 Redis 共享态（支持多 worker 跨实例校验）；未配置 `REDIS_HOST` 或连接失败时自动回退进程内实现（本地 Map / MemoryStore），行为与迁移前一致。

因此：

```env
REDIS_HOST=127.0.0.1
REDIS_PORT=6379
REDIS_PASSWORD=替换为密码
REDIS_DB=0
```

配置上述变量后即生效，无需重启依赖补丁。**明确不迁移**的跨实例面（P1-1 结论）：WebSocket 连接对象与在线状态、指标高频计数、安全告警 Map、`avatar.js` 自造令牌桶——仍为进程内实现，PM2 请保持单实例（`ecosystem.config.js` 已锁定）。生产启用 Redis 需 ACL/TLS 或内网隔离，不得公网裸奔。

## 八、Swagger/API 文档

Swagger 默认**任何环境都不挂载**（避免暴露接口结构，也允许 `npm ci --omit=dev`）。需要查看 API 文档时，在 `.env` 显式开启，且文档访问自身要求主站**超级管理员**登录（P2-169：/api-docs 与 /api-docs.json 均叠加 `requireSuperAdmin` 鉴权）：

```text
ENABLE_SWAGGER=1   # 开启后：GET /api-docs、GET /api-docs.json（需 super_admin 会话）
```

未开启时生产运行时不会挂载，无需在反代层屏蔽；若开启了又希望公网彻底不可达，可在反代层加白名单：

```nginx
location ^~ /api-docs { return 404; }   # 可选：公网拒绝外网
```

Swagger 相关包位于 `devDependencies`，因默认不加载，部署可省略它们（`npm ci --omit=dev`）；若开启 `ENABLE_SWAGGER=1` 而依赖被省略，加载失败会按日志提示回退（不挂载，服务不受影响）。

## 九、生产安全必检

当前代码已有 CSP、安全响应头、限流、上传签名检查、CSRF 和管理员路由保护，但这些不等于部署默认安全。上线前至少完成：

1. **密钥持久化**：设置强随机 `SESSION_SECRET` 和严格 64 位十六进制 `ENCRYPT_KEY`；限制 `.env` 权限并安全备份、轮换。
2. **CORS 白名单**：必须设置准确的 `CORS_ORIGINS`，例如 `https://jingtu.example.com`；多个来源用英文逗号连接且不要夹空格。未设置时当前 `cors` 配置会接受请求来源并允许凭据，不适合公网生产。
3. **HTTPS 与代理信任**：TLS 终止、HTTP 跳转、`trust proxy`、客户端 IP、限流及安全 Cookie 必须联合验证；当前 Cookie `secure` 条件需修正后才能宣称生产安全。
4. **Cookie 检查**：实际登录后用浏览器确认 `connect.sid` 带 `Secure; HttpOnly; SameSite=Lax`，退出能清除同一 Cookie，且 HTTP 不会发送它。
5. **API 文档限制**：阻止公网访问 `/api-docs` 和 `/api-docs.json`，除非明确需要且已加认证。
6. **数据库隔离**：最小权限账号、仅内网/本机监听、强密码、慢查询与容量监控。
7. **备份**：自动化、加密、异机保存并做恢复演练；不能把“存在备份路由”当成已完成备份。
8. **文件与日志**：服务账号只写必要目录；日志、备份和上传文件不得由 Web 静态路由直接公开。
9. **CSP 现状**：当前 `script-src` 仍允许 `'unsafe-inline'`，不能描述为严格 CSP；收紧前需迁移剩余内联代码或采用 nonce/hash。
10. **防火墙**：公网只开放实际需要的 SSH/HTTP/HTTPS；3456 仅监听受控网络或由主机防火墙限制，3306 不对公网开放。

### 10.1 更新

cd /srv/jingtu-web

更新前先完成数据库和上传文件备份。不要把数据库迁移等同于可逆操作；代码回滚前确认数据库模式的向后兼容性。

### 10.2 检查清单

| 频率 | 检查 |
|---|---|
| 每次部署/发布 | 有反向代理必须设置 `TRUST_PROXY` 为实际跳数（如 `1`）；未设置默认 `false`，全部客户端 IP 会坍缩为 `127.0.0.1`，限流/告警/审计失真 |
| 每天 | `/api/health/ready`、进程状态、错误日志、磁盘和证书告警 |
| 每周 | 备份任务结果、异机副本、慢查询、安全告警和依赖公告 |
| 每月 | 在隔离环境执行恢复演练，检查容量、权限、密钥和证书续期 |

### 10.3 回滚

不要对共享仓库强制重置或覆盖未提交改动。生产回滚应部署经过标记的已知版本，并按变更方案处理数据库：

```bash
cd /srv/jingtu-web
git log --oneline -5
git checkout <已验证的发布标签或提交>
cd server
npm ci
pm2 restart jingtu-web
curl -fsS http://127.0.0.1:3456/api/health/ready
```

### 10.4 常见故障

| 现象 | 首要检查 |
|---|---|
| 开启 `ENABLE_SWAGGER=1` 后启动报缺少 `swagger-jsdoc` | 是否错误使用了 `npm ci --omit=dev`（默认不加载，可忽略该提示） |
| Node 18 安装或启动失败 | 升级到 Node 20.9.0+，删除旧 `node_modules` 后重新 `npm ci` |
| 端口已监听但站点不可用 | 请求 `/api/health/ready` 并检查 MySQL，而非只看端口 |
| MySQL 8 启动失败且提示 query cache | 删除 `query_cache_type/query_cache_size` 配置 |
| 反代后限流/IP 异常 | 检查代理头和应用 `trust proxy` 配置，不要盲目信任所有代理 |
| 生产登录 Cookie 不带 Secure | 已由 `secure:'auto'` + `trust proxy` 修复；确认 `TRUST_PROXY` 与反代 HTTPS 正确即可 |
| Redis 配置后仍无共享态 | 确认 `REDIS_HOST` 可达（`redis-cli ping`）、服务进程已重启；`cache.initCache()` 已在入口调用，连接失败会静默回退进程内实现（看启动日志「缓存初始化异常」） |
| `start-services.sh` 健康检查警告 | 脚本请求的 `/api/health` 端点已存在，按 200 判定；若仍告警请确认 Node 已启动、端口未被占用 |

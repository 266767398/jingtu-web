# 境途同游 Web 项目 — 后端架构详解

> 版本：V7.10（入口启动日志版本）  
> 最后更新：2026-08-25  
> 审计基准：当前工作树中的 `server/` 与 `public/` 实现；文件头中的 V5.2/V6.x 与健康接口中的 V6.29 是历史标记，不代表统一发布版本。

## 一、运行架构与真实启动流程

### 1.1 技术组成

| 层 | 当前实现 |
|---|---|
| HTTP | Node.js + Express 4，`http.createServer(app)`；入口本身不创建 HTTPS server |
| 数据库 | MySQL，`mysql2/promise` 连接池 |
| 会话 | `express-session`；优先 `express-mysql-session`，模块加载失败时回退 MemoryStore |
| 实时通信 | 同一 HTTP server 上的 `ws` WebSocketServer，路径 `/ws` |
| 外部实时源 | `wss://pipeline.vrchat.cloud/?authToken=...` |
| 缓存 | Redis 封装和业务缓存服务已存在，但当前入口没有调用 `cache.initCache()`，实际启动流程中缓存保持禁用 |
| 上传/媒体 | `multer`、`sharp`；另有 FFmpeg 依赖 |
| 邮件 | `notification-service.js` 直接初始化 Nodemailer；独立 `mailer.js` 当前未初始化 |
| 定时任务 | 当前只启动 `schedule.js`（`node-schedule`）；`tasks.js`（`cron`）仅被导入，未调用 `startTasks()` |
| API 文档 | Swagger UI `/api-docs`，JSON `/api-docs.json` |
| 前端 | `public/` 静态站点、PWA Service Worker、同源 REST 与 WebSocket |

`server/package.json` 没有 `engines`，因此代码库没有声明 Node.js 最低版本；不应把“Node ≥16”当成已配置约束。

### 1.2 启动顺序（`server/server.js`）

1. 从仓库根目录加载 `.env`，导入各模块；`db.js` 在导入时创建不带 database 的连接池并启动 15 秒数据库心跳。
2. 创建 Express app 与纯 HTTP server；默认端口 `3456`，监听地址稍后为 `0.0.0.0`。
3. 创建 `uploads/profile/photos`、`uploads/profile/videos`，设置 `timeout=120000`、`keepAliveTimeout=5000`、`headersTimeout=60000`。
4. 按第二章顺序注册全局中间件、静态目录、会话、限流、初始化/CSRF 端点和 CSRF 校验。
5. 创建 VRChat Pipeline，绑定通知/用户/好友事件；同步读取 `server/session.json`，解密或迁移旧明文 Cookie，并在取得 authToken 时立即连接 Pipeline。
6. 按第三章顺序挂载业务路由和最终错误处理中间件。
7. 把 `/ws` WebSocketServer 绑定到 HTTP server，并连接通知、安全告警服务引用。
8. 注册 SIGTERM/SIGINT/SIGHUP、`uncaughtException`、`unhandledRejection` 处理器。
9. 调用 `db_init.js`。成功后向 `schedule.js` 注入通知服务与 VRChat Cookie 获取函数并启动任务；失败只记录警告，跳过任务。
10. 无论数据库初始化是否成功，都执行 `server.listen(PORT, '0.0.0.0')`。

因此 Pipeline 与站内 WebSocket 都在数据库初始化之前设置；数据库初始化失败不会阻止 HTTP 服务启动。

## 二、中间件、静态资源与安全边界

### 2.1 精确注册顺序

1. `cors`：`CORS_ORIGINS` 存在时直接按逗号 `split(',')`（HTTP 侧不 trim），否则 `origin: true`；`credentials: true`。
2. `compression`：level 6、threshold 1024；请求带 `x-no-compression` 时跳过。
3. 手工响应头：`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: strict-origin-when-cross-origin`、CSP；仅生产环境添加一年 HSTS。
4. `/api` 全局 DDoS limiter：每 IP 每分钟 600 次，跳过 OPTIONS。
5. `suspiciousRequestDetector`：拦截 WordPress、`.env`、`.git`、phpMyAdmin、shell/cmd 等路径并返回 JSON 404。
6. 自定义 WAF：检查 URL、body、query、params 中的 SQL 注入、XSS、路径穿越、LFI/协议、命令注入和扫描器模式。
7. `metricsMiddleware`。
8. `apiVersionMiddleware`。
9. `requestSizeLimiter`：请求体大小全局卡口，阈值（`req_max_upload_mb` / `req_max_body_mb` / `req_max_other_mb`）自 2026-08-16 起由超管后台「系统设置」可调（见 `server/settings.js` + `docs/08` §4.7）。
10. `express.json({ limit: '20mb' })`；没有全局 urlencoded parser 或 cookie-parser。
11. UTF-8 响应头包装器（为 `text/*` 且无 charset 的 Content-Type 追加 UTF-8）。
12. 静态目录（见 2.2）。
13. `GET /api/avatar/default`。
14. Session。
15. `/api` 用户存在/封禁校验。
16. 登录、上传、管理、搜索分级限流。
17. `GET /api/auth/check-init`。
18. `GET /api/csrf-token`。
19. `/api` CSRF 校验。
20. 业务路由、Swagger、最终四参数 500 错误处理器。

### 2.2 静态目录顺序

| URL | 文件目录 | 说明 |
|---|---|---|
| `/uploads` | 根目录 `uploads/` | 默认 `express.static` 选项 |
| `/assets` | 根目录 `assets/` | 默认选项 |
| `/` | `public/` | `maxAge: 0`、`etag: false` |

静态目录都在 Session、API 账户校验与 CSRF 之前。备份目录不再静态公开，只能通过管理员备份 API 下载。应用没有 SPA fallback，也没有显式 404 handler；未匹配请求由 Express 默认 404 处理。

### 2.3 请求大小与限流

- 声明的 `Content-Length` 超过 20 MiB：直接 413。
- 普通 POST/PUT 超过 5 MiB：413；路径包含 `/upload`、`/photos` 或 `/videos` 时绕过 5 MiB 分支，但仍受 20 MiB 全局分支影响。
- JSON parser 自身另有限制 20 MB。各 Multer 路由还可有自己的文件大小限制，例如群组图片 10 MiB。
- 登录：15 分钟 5 次，`skipSuccessfulRequests: true`；挂在 `/api/auth/login`、`/api/auth/vrchat-login`、`/api/login`。
- 上传：每分钟 10 次；挂在相册上传、资料照片/视频上传、群组图片。
- `/api/admin` 及 `/api/database|migration|backups|export|files|config`：每分钟 30 次。当前绝大多数实际管理路径是 `/api/admin/...`。
- `/api/search`：30 秒 20 次。
- 密码重置相关路由还使用 `middleware/rate_limit.js` 的 15 分钟 5 次限制。

### 2.4 Session、认证与角色

Session 选项为 `resave:false`、`saveUninitialized:false`、`rolling:true`，Cookie 为 7 天、HttpOnly、SameSite=Lax。MySQL Store 使用 `sessions` 表并允许自动建表；只有 Store 模块构造抛错时才回退 MemoryStore。

`SESSION_SECRET` 缺失时，HTTP Session 与 `ws_service.js` 都可能各自生成进程内随机值，不能保证 WebSocket 能验签 HTTP 会话。Cookie 的 `secure` 使用 `'auto'`：当请求经 HTTPS（`req.secure`，由 `trust proxy` 解析 `X-Forwarded-Proto` 决定）时自动带 `Secure`，纯 HTTP 则不带。入口已设置 `app.set('trust proxy', …)`（受 `TRUST_PROXY` 控制，生产默认 `1`）。代理部署只要正确终结 TLS 并设置 `X-Forwarded-Proto`，生产 Cookie 即安全可用。

每个 `/api` 请求若 Session 含 `userId`，会查询 `users`，发现用户不存在、软删除或封禁则销毁 Session 并返回 401；数据库查询失败时**fail-closed**（返回 `503`），不再放行，避免 DB 抖动期间被封禁用户绕过校验（2026-08-27 加固）。

`server/auth.js` 的权限模型：

| 角色 | 等级 |
|---|---:|
| `member` | 2 |
| `admin` | 3 |
| `super_admin` | 4 |

- `requireAuth` 判断 `session.userId !== undefined`。
- `requireRole(...roles)` 使用 `session.role` 和等级比较，要求达到传入角色中的最高等级。
- `requireAdminCompat` 要求等级至少为 admin。
- 密码后端要求至少 8 位，并包含小写、大写、数字；后端不要求特殊字符。`public/js/main.js` 的前端校验额外要求特殊字符，两端当前不一致。
- bcrypt cost 为 12。QQ 号用 AES-256-CBC；VRChat Cookie 用单独的 AES-256-GCM 方案。

### 2.5 CSRF

`GET /api/csrf-token` 生成 32 字节随机值的 hex 字符串，存入进程内 Map，TTL 1 小时；Token 可重复使用。每 15 分钟清理过期项，超过 10000 项时再删除一半最旧记录。

安全方法 GET/HEAD/OPTIONS 豁免。写请求的精确豁免为：

- `/login`、`/vrchat-login`、`/init`、`/2fa`；
- `/auth/login`、`/auth/init`、`/auth/logout`、`/auth/vrchat-login`、`/auth/forgot-password`、`/auth/verify-reset-code`、`/auth/reset-password`；
- `/logout`、`/csrf-token`；
- `/setup/test-db`、`/setup/test-email`、`/setup/save`、`/setup/state`、`/setup/reset`。

已建立 Session 时 Token 绑定 `sessionID`；匿名记录使用 `anon`，校验时不会执行 Session 匹配。前端通用 `api()` 对非安全方法先取 Token、带 `credentials:'include'` 和 `X-CSRF-Token`；migration 页面也通过专用包装器携带 Session 和 CSRF Token，setup 页面依赖安装阶段豁免。

### 2.6 其他安全实现及真实约束

- CSP 仍允许脚本和样式 `unsafe-inline`，允许 `connect-src 'self' ws: wss: https://api.vrchat.cloud`；没有 Helmet。
- 上传公共工具按扩展名/MIME 白名单过滤；`middleware/security.js` 的额外魔数校验仅在路由显式调用 `validateUploadFile` 时生效，不能概括为所有上传统一执行。
- SQL 大量使用参数占位符，但代码库也有动态 SQL；不能宣称“所有 SQL 均参数化”。
- `validation.js` 当前主要挂到 migration 的三个接口，不能宣称所有输入都经过统一校验。
- 系统 VRChat 的 `POST /api/login|2fa|logout` 统一要求管理员，并执行 CSRF 校验。
- migration 整个 Router 统一要求管理员；所有写操作同时执行 CSRF 校验。

### 3.2 路由家族与授权

- **认证**：`/api/auth/init|login|logout|session|vrchat-login|vrchat-2fa|forgot-password|verify-reset-code|reset-password` 为初始化/登录流程；change-password、VRChat 绑定/解绑要求登录。登录会 regenerate/save Session；登出 destroy 并清 Cookie。
- **资料**：`/api/profile` 下有本人统计、更新、导出、删除和个人相册/照片/视频管理；按用户查看资料/相册/视频的 GET 由处理器做可见性判断。
- **用户与权限**：`/api/users` 的列表、搜索、本人设置/位置及卡片等要求登录，用户管理多为 admin，创建用户为 super_admin；`/api/permission-groups/my` 要求登录，其余权限组定义、授权、成员关系为 super_admin。
- **内容**：posts 的列表/搜索/详情/评论列表公开，写入/点赞/评论要求登录；announcements 的读取公开，写入、附件、历史/恢复为 admin；events 多数读取公开，报名/评论/创建要求登录或处理器校验，更新、同步、签到/QR、归档为 admin；删除（单删 `DELETE /api/events/:id` 与批量 `POST /api/events/batch-delete`，08-22 起共用 `deleteOneEvent` 校验）为管理员或创建者本人，批量删除先全量预校验（越权/已结束/不存在任一不过即整体拒绝）。
- **相册**：`routes/album` 在 `/api` 下声明 `/album/*` 和 `/photos/*`；读取大多公开，分类/回收站/永久删除为 admin，上传、互动和编辑采用登录/所有者手工检查。部分身份解析会在无 Web Session 时回退到系统 `authState.userId`。
- **社交功能**：checkin、achievements、user-like、favorites、event-teams 均要求登录；favorites 的推荐管理要求 admin，event-teams 另做队主校验；新增 friends（好友申请/响应/拉黑/互关/共同好友）、follows（关注/粉丝）、collections（统一收藏馆）均要求登录，collections 的管理端点使用 `requireAdminCompat`。
- **聊天/直播**：chat 全家族经聊天认证并包含私聊、群组、成员、搜索、批量已读、编辑/删除；live 的列表/详情/点赞数公开，创建、开播、结束、进入/离开、评论、历史和删除要求登录。
- **VRChat/群组**：`/api/login|2fa|logout` 是系统 VRChat 状态接口；groups 提供 lookup、world/avatar、群资料、名册、状态、邀请和同步，具体端点混合公开/登录/管理员校验。
- **通知**：列表和未读数在无身份时返回空结果；多数写操作手工取身份，部分也会回退系统 VRChat 用户；设置和单条删除要求正常登录。
- **管理**：实际管理 API 为 `/api/admin/db/*`、`/api/admin/backups/*`、`/api/admin/config/*`、`/api/admin/files/*`、`/api/admin/export/*`、`/api/admin/analytics/*`、`/api/admin/webhooks/*`、`/api/admin/logs/*`、`/api/admin/security/*`，均要求管理员。
- **健康**：`/api/health` 公开并返回系统 VRChat 登录摘要；`/api/health/live` 公开；`/api/health/ready` 查询 DB；`/api/health/detailed` 要求 admin。`db.js` 导出当前连接池访问函数，ready/detailed 可执行实际数据库探测。
- **安装**：`GET /api/setup/check` 公开，返回 `{configured,wizardCompleted,authenticated,isSuperAdmin}`。首次安装（`.env` 不存在）开放 test-db/test-email/save/state；**重走（reconfigure，`.env` 已存在）模式**下 test-db/test-email/save 与 `POST /api/setup/reset` 要求 `super_admin` 角色（`requireSuperAdminForReconfigure`），`reset` 仅清空隔离存储的 `setup-wizard.json`、不动 `.env`/数据库。save 为合并写盘（仅覆盖已填项，失败不再删 `.env`），要求目标库已存在 `users` 表，不执行 `db_init`，也不重启进程。
- **迁移**：全部端点要求管理员；写操作要求 CSRF Token。前端“停止迁移”只改变页面变量，不中止已经发出的请求。
- **分享**：Router 内部再次使用 `/share`，所以有效路径是 `/api/share/share`、`/api/share/share/:code`、`/api/share/share/list`；且参数路由 `/:code` 位于 `/list` 前，GET list 会被当作 code 匹配。
- **站点文件**：`/sitemap.xml`、`/robots.txt` 由 sitemap router 提供。

### 3.3 `public/` 对接方式

- `public/index.html` 以传统全局脚本加载功能模块；`public/js/core.js` 的 `api()` 统一同源 fetch、Cookie、10 秒超时、JSON body、CSRF 与 401/403/429 处理。
- 首页初始化实际调用 `GET /api/auth/init`，不是 `server.js` 中较早注册的 `/api/auth/check-init`。
- 各模块直接对应 auth/profile/users/posts/announcements/events/album/chat/live/favorites/checkin/achievements/groups/admin-db 等路由家族。
- `public/setup.html` + `public/js/setup.js` 对接 setup 检测、DB/SMTP 测试和保存；“保存并启动”只是保存配置后跳转，不启动新进程。
- `public/migration.html` 内联脚本对接 detect、连接测试、数据库/表枚举、migrate、scan-config、replace-config。
- Service Worker `jingtu-v1` 预缓存少量核心资源，对带 `?v=` 版本号的 JS/CSS 采用 cache-first、对同源非 `/api/` 其余请求网络优先缓存兜底（现已由 `index.html` 在 `window load` 后注册启用）；API 明确不缓存。

## 四、数据库与初始化

### 4.1 连接池

`db.js` 默认：host `127.0.0.1`、port `3306`、user `root`、database `jingtu_group`、timezone `+08:00`、charset `utf8mb4`。连接池为 `connectionLimit:10`、`queueLimit:50`、keepalive 10 秒。密码会 trim 并移除成对的首尾引号。

启动先创建不带 database 的池；`db_init.js` 建库后调用 `recreatePool()` 切换到目标库。`holder.pool` 使模块在重建后读取新池。15 秒心跳失败时最多进行 3 次重建，每次失败等待 3 秒。

### 4.2 `db_init.js` 行为

1. 临时连接 MySQL，最多尝试 3 次；失败间隔实际为 2 秒、4 秒。
2. `CREATE DATABASE IF NOT EXISTS ... CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci`。
3. 重建目标库连接池。
4. 发出 `SET FOREIGN_KEY_CHECKS = 0`，创建/迁移表，最后恢复为 1。该设置是连接级的，而后续通过 pool 多次查询，不能保证所有语句使用同一连接。
5. 执行约 70 个 `CREATE TABLE IF NOT EXISTS`，随后兼容性 `ALTER TABLE`、索引补全以及默认权限、权限组、系统配置、签到奖励、成就等种子数据。

约 70 张代码定义表为（基线 55 张 + 新增社交/收藏相关表，如 `user_friends`、`user_follows`、`collections`、`collection_folders`、`collection_ratings`、`model_ratings`、`model_tag_dict` 等）：

## 五、缓存、通知、邮件、Webhook、日志与文档服务

### 5.1 Redis/缓存

`cache.js` 只有在调用 `initCache()` 且设置 `REDIS_HOST` 时才连接 Redis；默认 port 6379、DB 0、空密码。get/set/del/keys/flush 和通用 JSON cache middleware 都在禁用或错误时降级为空结果/无操作。

`cache_service.js` 定义用户、在线状态、活动、动态、照片、公告、配置、统计、世界、资料卡、群名册等 key 和 30 秒至 24 小时 TTL，也提供每日 warmup。**当前 `server.js` 仅导入 cache/cacheService，没有调用 `cache.initCache()`，也没有挂通用 cache middleware，因此本入口启动时 Redis 缓存实际不工作。** 每日预热和每 5 分钟在线名册写入会退化为空操作。

当前 events/posts 的若干写路由调用 `cacheService.del()`，而该服务未导出 `del`；执行这些分支会抛 `TypeError`。这是现有实现状态，不应文档化为已正常完成缓存失效。

### 5.2 通知与邮件

`notification-service.js` 在模块实例化时读取 `SMTP_HOST/PORT/USER/PASS/SECURE/FROM`，配置完整才创建 transporter。通知先写 `notifications`，再按用户设置推送站内 WebSocket，并可发送邮件；设置缓存为进程内 Map，显式失效，无 TTL。

独立 `mailer.js` 使用 `SMTP_PASSWORD`（与通知服务/认证重置邮件使用的 `SMTP_PASS` 不同），支持队列重试和系统告警；但入口没有调用 `initMailer()`。因此 `tasks.js` 中依赖它的邮件能力不属于当前已启动链路。

### 5.3 Webhook、Swagger、日志

- `webhook.js` 支持多类事件、HMAC-SHA256 签名、5 秒请求超时和并行投递；当前主要由动态和活动写操作触发，并非所有定义事件都有调用点。
- Swagger 为 OpenAPI 3，挂载 `/api-docs` 和 `/api-docs.json`；扫描相对路径 `./routes/*.js`，结果依赖进程工作目录。
- `logger.js` 默认开发 DEBUG、生产 INFO，可用 `LOG_LEVEL` 覆盖；缓冲达到 100 条或每秒刷盘，目标文件 10 MB 时轮转。仍有大量模块直接使用 `console.*`。
- 轮转文件名为 `date.log.1`，但归档扫描只接受以 `.log` 结尾的文件，因而“可靠保留最近 5 个归档”并未由当前实现保证。

## 六、站内 WebSocket（`ws_service.js`）

### 6.1 握手与身份

`WebSocketServer({ server, path:'/ws', verifyClient })` 复用 HTTP server。握手解析 `connect.sid`，若值以 `s:` 开头则用 `SESSION_SECRET` 验签，再从独立 MySQL Session Store 读取 Session，必须含 `userId`；连接身份固定为 `req.wsUserId`，忽略消息中的 userId。未带 `s:` 的 SID 不会验签。

生产环境只有在 Origin 非空、白名单非空且不匹配时才拒绝；缺失 Origin 会放行。白名单来自 trim 后的 `CORS_ORIGINS`，并追加当前端口 localhost/127.0.0.1。

### 6.2 消息与心跳

服务端接受：`pong`、`online`、`offline`、`location:update|stop`、`chat:send|typing`、`group:send`、`group:location:update|stop`、`history:request`。私聊会存 `messages`；群发送检查成员身份；群历史读取和群位置更新当前没有同等的成员校验。群成员校验缓存 TTL 60 秒。

每连接每 30 秒收到 JSON `{type:'ping'}`；只有收到 `{type:'pong'}` 才刷新 `lastPing`，10 分钟未刷新会把用户全部连接强制下线。另有每 30 秒离线摘要任务，可能向在线用户重复推送最近 5 分钟摘要。

当前 `public/js/main.js` 每 25 秒发送 `{type:'ping'}`，却不处理服务端 `ping`、不回复 `pong`；服务端也不处理客户端 `ping`。因此按当前 public/server 组合，活跃连接仍可能在约 10 分钟后被判超时。浏览器重连最多 10 次，指数退避上限 30 秒。

## 七、VRChat API 与 Pipeline

### 7.1 双层身份

`getVRCCookie(req)` 优先使用用户 Session 中的 `vrchatCookie`/`vrcCookie`（尝试解密），否则回退系统 `authState.cookie`。系统状态由 `/api/login|2fa|logout` 和 `server/session.json` 管理；用户绑定登录走 `/api/auth/vrchat-*`。

VRChat Cookie 使用 `ENCRYPT_KEY`（64 hex/32 字节）的 AES-256-GCM：`enc:` + Base64，其中依次为 12 字节 IV、16 字节认证 tag、ciphertext。旧的非 `enc:` 值可作为明文读取并原子重写为加密格式。

### 7.2 Pipeline

从 Cookie 正则提取 `authcookie_...` 后连接 `wss://pipeline.vrchat.cloud/?authToken=...`，User-Agent 当前是 `JingTuWeb/5.2`。支持 notification、user、friend、instance、system 与 unknown 事件；最多重连 10 次，初始 5 秒并乘 1.5。

入口把 Pipeline 通知广播给站内 WS；`group.announcement` 还写入公告表，friend 事件广播。`broadcastGroupStats()` 虽已定义，但当前没有定时或直接调用。`disconnect()` 的 close 事件仍可能安排重连，因为没有主动关闭标志。

### 7.3 401 降级与 Cookie 失效处理（2026-08-16 修复）

`vrcWithFallback(req, run)` 是实时调用 VRChat 的统一降级出口：当 `run(cookie)` 返回 401，先用 `getUserVRCCookieFn(req)` 判定该 cookie 是否来自**当前用户自身绑定**——仅当用户自身 cookie 失效时才 `await invalidate(req, cookie)` 并降级到系统账号 cookie 重试；若 cookie 实际来自系统账号兜底（用户未绑定 VRChat 的常态），**绝不调用 invalidate**，只降级重试，避免把系统级 Cookie 误注销（修复前 401 会无条件清除系统 Cookie，导致全员实时同步中断）。

`invalidateVRCCookie(req, deadCookie)` 现改为 `async`：清除用户 Session 中的 VRChat cookie 后 `await req.session.save()` 持久化，刷新后保持生效。系统账号登录态由 `vrc_system.js` 独占管理，不再经此函数清除。

模型失效扫描 `scanInvalidModels(opt)` 加模块级 `scanInFlight` 互斥，避免每日定时与手动扫描并发触发双通知。30 秒在线刷新任务在开头探活系统 cookie，401 则 `console.warn` 并跳过本轮，仅保留现有在线状态，不再误标全员离线（`GET /group/members/refresh` 同步修正：系统 cookie 探活失败即跳过、聚合计数排除 skipped 成员）。

## 十、错误处理与关闭

### 10.1 错误响应现状

`utils.js` 提供 `sendError`/`handleError` 的嵌套格式：

```json
{ "success": false, "error": { "code": "...", "message": "..." } }
```

但路由仍混用 `{error:"..."}`、`{success:false,error:"..."}` 等格式。最终全局错误处理器总是返回 500，开发环境回显 `err.message`，其他环境返回“服务器内部错误”，不保留 `err.status`。`safeError` 在非生产环境返回原消息，在生产环境返回“操作失败，请稍后重试”。因此当前没有全 API 统一错误契约。

`unhandledRejection` 只记录并继续运行；`uncaughtException` 记录后尝试结束 pool（未 await）并退出 1。

### 10.2 关闭流程

SIGTERM/SIGINT/SIGHUP 调用：

1. `server.close(callback)`；
2. 清 CSRF 定时器；
3. 关闭站内 WS 客户端/server及其定时器；
4. await MySQL pool.end；
5. 取消 `schedule.js` jobs；
6. 立即 `process.exit(0)`。

当前流程没有 await HTTP/WS close callback、没有重复信号保护或强制超时，也没有关闭 VRChat Pipeline、Redis、mailer、数据库心跳定时器，且没有显式 await `logger.flush()`。不能把它描述为已完整释放全部资源。

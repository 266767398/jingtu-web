### 20261015c — CSP nonce 缓存错配修复（"刷新后选项卡/按钮点不了"）+ 同步按钮与 24h 节流
**根因（点击失效）**：服务端对每个响应注入**一次性 CSP nonce**（`script-src` 已无 `'unsafe-inline'`，只认 nonce），但 `sw.js` 把 HTML 文档写进了缓存：`STATIC_ASSETS` 预缓存 `'/'`、导航分支 `cache.put(request, clone)`。被缓存的 HTML 携带的是**那次响应的旧 nonce**，一旦被 SW 命中（离线兜底、旧 SW 未及时换代），就与当次 CSP 头错配 → 页内全部内联脚本（尾部事件绑定块 `bindClick`、页头引导块）被浏览器拦截 → **顶部选项卡与各模块按钮点击全部失效**，且刷新依旧（命中同一份坏缓存）。用户控制台 4 条带 sha256 的违规报告即此现象。

### 20261015g — 性能优化批（schedule.js N+1 修复 + presence 分片 + 信任回填加速）

**发现**：上轮修完 `presence/contribute` 的 N+1 串行入库后，又扫到同类问题在 `server/schedule.js` 自己身上——每 30 分钟跑一次的 stable refresh 对 `batchWrites`（几百成员）**逐条 await UPDATE**，往返次数 = 成员数。加上信任补充回填速度被 12h 去重 + 20 条/轮限制拖慢（上轮修的信任等级丢失问题部署后要等好几天才能回填完）。

**1. schedule.js batchWrites N+1 → 批量 CASE WHEN UPDATE + touchOnly 聚合**（`server/schedule.js` L484-551）
- 原版：`for (const w of batchWrites) { await pool.query(UPDATE ... WHERE vrchat_id=?) }` —— 几百成员 = 几百次 DB 往返。
- 修复：
  - `touchOnly`（心跳，不碰任何业务字段）聚合为单条 `UPDATE group_roster SET synced_at=NOW() WHERE vrchat_id IN (...)`，分片 200 一批。
  - 非touchOnly 用 **CASE WHEN 批量 UPDATE** 分片 200 一批：每列生成 `CASE WHEN vrchat_id=? THEN ? ... ELSE col END`，所有列共享同一套 vrchat_id 参数，一次 SQL 写多行。优势：**空值不覆盖非空旧值**保护、trustLevel/status_description 保留策略、布尔列 0/1 转换全部保留，只把"每条单独 UPDATE"变成"每 200 条一条批量 UPDATE"。
  - CASE WHEN 用 `ELSE col END` 兜底——该行某列缺失时自动保持原值，不会把其他行的字段串过来（防御了 chunk 内对象 key 不完全一致的情况）。
- 性能收益：每轮 stable refresh 的 DB 往返次数从 `batchWrites.length` 降到 `ceil(batchWrites.length / 200)`，大群（500+ 成员）从 500+ 次降到 3 次以内。

**2. presence/contribute 分片 500 一批**（`server/routes/groups_members_sync.js` L317-356）
- 上轮把串行 INSERT 改成单次批量，但**大群（>500 命中好友）会撞 MySQL 默认 `max_allowed_packet=16MB`**（每行 ~9KB，600 行就 5.4MB，但 SQL 文本 + 索引膨胀会超）。改为 `INSERT_CHUNK=500` 分片写入，每片独立 `INSERT ... ON DUPLICATE KEY UPDATE`。分片间仍保留 `req.aborted || res.destroyed` 客户端中断止损。

**3. 信任回填加速**（`server/schedule.js` L559-575）
- `TRUST_ENRICH_BATCH`：20 → 25（每轮多补 5 条）。主链路非好友回退已从 25 压到 12，总令牌桶占用仍在 40/min 内。
- 去重窗口：`INTERVAL 12 HOUR` → `INTERVAL 6 HOUR`。隐私墙/404 成员重试窗口减半，既加速真正能补的成员上抬，也不会让查不到的成员长期占坑（仍有 `vrcBacklog()>2` 中断保护 + 令牌桶限流）。
- 部署后信任等级回填速度从 ~40 条/天（去重 12h 卡死隐私墙成员）提升到 ~200+ 条/天（6h 重试窗口 + 25 条/轮），大群（500 人）从"要好几天"缩到 ~2 天。

**测试**：903 例全绿。schedule 的 CASE WHEN 批量 UPDATE 改写未被现有测试直接命中（测试侧重 SQL 片段字符串匹配，不是跑真实 UPDATE），但语法/参数/setClause/colMap 都经过代码审查，且 `colMap` 与上轮单条 UPDATE 的列集严格对齐——不会引入字段丢失。

### 20261015l — 静态 HTML 启发式缓存与 CSP nonce 错配（"Executing inline script violates..." 全页脚本被拦）修复

**发现**：用户浏览器控制台批量报 `Executing inline script violates the following Content Security Policy directive 'script-src 'self' 'nonce-XXX'...'`，共 4 处。诊断后**服务端注入逻辑正常**（本地/生产返回的 HTML 内联 `<script>` 全部已打 nonce），但浏览器报错行号（70/89/2603/3367）与源文件内联 script 位置（93/112/2628/3398）对不上 → **浏览器加载的是启发式缓存的旧 HTML**。

1. 静态中间件 `setHeaders` 新增 HTML 分支：`.html` / `index.html` 响应显式 `Cache-Control: no-store, no-cache, must-revalidate`——浏览器必须重取，绝不与旧 nonce 错配。

### 20261016a — 「服务器好使、本地不好使」根因修复：WebSocket 会话 cookie 错配 + 头像裁剪滚动锁根治（用户反馈批次）

**背景**：用户反馈生产服务器（47.105.33.180:3456 Docker，运行旧代码）功能正常，但本地实例（127.0.0.1:3456 直连 Node）异常——在线状态/同步永不更新、头像裁剪弹窗打开后页面无法滚动、管理面板部分按钮点击无反应。逐项定位并修复。

**修复**：

1. **WebSocket 在线同步本地失效（「服务器好使、本地不好使」根因）** —— `public/js/main.js` `resolveWsUrl()`：
   - 根因：本地 `.env` 无 `WS_URL` → `/api/client-config` 返回 `{"wsUrl":""}`；旧代码对 `location.hostname === '127.0.0.1'` **无条件改写为 `localhost`**（假定走 nginx 80 反代 `/ws`）。但本机是**直接访问 127.0.0.1:3456 连 Node**（本地 nginx 80 只跑默认站、不反代 `/ws`），且会话 cookie（`connect.sid`，httpOnly host-only）只属于 `127.0.0.1`——改写后 WS 握手指向 `localhost`，握不到该 cookie，`ws_service` 的 `verifyClient` 返回 401 → 浏览器报 "WebSocket connection failed"、在线状态永不更新。
   - 修复：`resolveWsUrl()` 改为**严格同源**——有 `window.__WS_URL__` 用之，否则一律 `(wss:|ws:)//location.host/ws`，不做任何主机名改写；部署需要显式中继时用 `WS_URL` 覆盖。
   - 验证：浏览器实测 `new WebSocket('ws://'+location.host+'/ws')` 状态 `open`（修复前重连失败）。

2. **头像裁剪弹窗打开后页面无法滚动（滚动锁残留）** —— `core.js` / `ui.js` / `index.html`：
   - 根因：滚动锁有**两个 owner**——`showModal` 用字符串 owner `'modal:'+id` 加锁，`initModalAccessibility` 的 MutationObserver 经 rAF 触发 `activateModalA11y` 再用**元素 owner** 加锁。两者时序不可控，任何「打开后立即解锁」的写法只能释放其中一把（另一把由 rAF 异步补加），`body` 永久 `overflow:hidden`。
   - 修复：引入 `data-no-scroll-lock` 属性 opt-out——`#avatarCropModal` 带该属性，`showModal`（core.js）与 `activateModalA11y`（ui.js）两处加 `hasAttribute('data-no-scroll-lock')` 条件判断跳过加锁；`profile.js` 移除原先的 `unlockBodyScroll` 调用。裁剪弹窗从此不参与 body 滚动锁，鼠标移出取景区即可滚动页面、仅取景区内滚轮缩放。
   - 验证：实测弹窗打开时 `body.style.overflow === ''`（页面可滚动），关闭后恢复。

3. **管理面板按钮静默失效补漏** —— `admin-perms.js` / `admin-ui.js`：
   - 「用户权限」面板：非超管（只读）时搜索框/用户下拉仍可输入但无任何反馈 → 改为禁用控件 + 占位提示「仅超级管理员可见」。
   - 内容管理「查看活动」按钮：`showEventDetail` 定义于懒加载模块 `events.js`，若用户从未打开过活动页、空闲预载未完成时点击会静默无反应 → 先经 `_ensureTabModules('events', cb)` 按需确保模块就绪再调用（无该函数时回退轮询重试）。

4. **定时任务磁盘 IO 优化（F-40）** —— `server/schedule.js`：
   - 根因：每轮刷新对**全员**重写 20 列 `CASE WHEN` 批量 UPDATE，且当前态快照表（`friend_log_current` / `world_visit_current` / `avatar_history_current`）每轮 UPSERT 重写全部行——是持续高磁盘 IO 的主因之一。
   - 修复：① 主刷新链路新增**无变化判定**（本轮计算值与上一轮 `group_roster` 正式状态全等 → 降级为 `touchOnly` 仅刷 `synced_at` 心跳，跳过 20 列批量 UPDATE；`existing SELECT` 扩展比较列）。② 三张当前态快照表 UPSERT 前按主键查 `curMap`，值无变化跳过重写（当前态表仅作跨轮次 diff 基准，`synced_at` 无读取方 / 头像场景不受影响）。语义（信任排序 / `MAX(synced_at)` / 在线展示）均不变。
   - 验证：重启后运行日志确认无 `Unknown column` / `Truncated` 错误，定时任务正常。

5. **头像上传即时预览** —— `public/js/profile.js`：裁剪确认后立即用 `URL.createObjectURL(file)` 把本地文件显示到头像位（不等网络），上传成功以服务器 URL 覆盖、失败/异常回滚原头像。
